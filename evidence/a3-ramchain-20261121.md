## 1. 目标与验收标准

目标：在不写 flash 的前提下，验证 A3 定制 U-Boot（RAM 链）的 slot-aware 启动逻辑与 SPI-NAND/env 只读路径。

验收标准（uboot-port/a3-slot-boot-design.md §8 与 uboot-port/README.md §5）：

1. A3 banner 出现在串口，包含唯一 commit token；提示符可用（help/version）。
2. e2631boot info 正确打印两个槽位的分区偏移、serial、version、header chip 偏移，并给出 slot1 决策。
3. e2631boot load 选中 slot1 uImage，校验 header/data CRC 后装入 RAM，不执行。
4. mtd 命令只读可用，读回的槽位头部/env 与运行中 Linux 的参考切片逐字节一致。
5. env 只读：printenv 显示厂商 env 在 RAM 中被覆盖为 bootcmd=e2631boot，saveenv 不存在。
6. 零 flash 写入：全程只允许读命令，mtd0 sha256 与基线一致；设备恢复 Linux 后健康。
7. recovery：reset_cpu 在本 SoC 为 no-op，需用户断电；恢复后抓取链恢复、无 panic、MT7916 ready。

## 4. 关键结果

### 4.1 banner 与加载完整性

- banner 行：U-Boot 2027.01-rc2-g8a9d1f7eecfa (Nov 21 2026 - 07:24:45 +0000)；两次会话一致。
- help 中可见 e2631boot、mtd、reset，且没有 saveenv；version 输出 g8a9d1f7eecfa 及 arm-none-eabi-gcc 13.2.1。
- xmodem 448,072 B 装载后，md.b 每 16 KiB 一块、共 28 块逐字节比较，mismatches=0、gaps=0（vendor 控制台无 crc32 命令，故以全镜像 md.b 为逐字节证据；A3 镜像内 crc32 在 0x100 范围可用，输出 660a59e8）。

### 4.2 e2631boot info（slot 语义与决策）

会话 2 raw 输出（会话 1 完全相同）：

```
e2631boot: slot0 at 0x00700000: serial 7, version "V1.0.0.7B5.8000", header 0x01c60000
e2631boot: slot1 at 0x02300000: serial 12, version "ImmortalWrt v1.10.0", header 0x03800000
e2631boot: cspboot would boot slot1
```

- at 0x... 是槽位分区偏移（slot0=0x700000、slot1=0x2300000），header 0x... 是版本头 chip 偏移（0x1c60000、0x3800000），与 DTS/分区表一致。
- slot0 为厂商槽（serial 7、V1.0.0.7B5.8000），slot1 为我们的槽（serial 12、ImmortalWrt v1.10.0）；serial 每次刷写递增（batch-2 刷写时为 11，当前 r0-86cddb7 为 12）。
- 决策 slot1；扫描耗时 0.81-0.82 s（判据 <3 s）；输出中无 Starting kernel / Booting kernel 标记（info 不启动）。

### 4.3 e2631boot load（uImage 校验与装载，不执行）

```
e2631boot: uImage "ARM ImmortalWrt Linux-6.18.60": load 0x40008000 entry 0x40008000, 3491146 bytes at 0x42000000
e2631boot: header and data CRCs are good
```

- 8/8 断言通过：uImage 行存在、名称含 ImmortalWrt、load/entry=0x40008000、dest=0x42000000、size=3,491,146（区间合理）、header+data CRC good、无 boot 标记。
- 耗时 4.61 s（含 SPI-NAND 读取与 CRC 校验）。

## 5. 异常、缺陷与修复

### 5.1 驱动解析器断言缺陷（会话 1 load 被跳过的原因）

- 现象：会话 1 中 e2631boot info 实际输出正确（与 §4.2 相同），但驱动断言 slot1_serial_11=False、两个 header 偏移断言=False，于是判定 info 不干净并跳过 load。
- 根因：驱动最初把 at 0x... 当作 header chip 偏移（实际是槽位分区偏移），并把 batch-2 刷写时的 serial 11 写死（每次刷写 serial 递增，当前为 12）。
- 修复：解析器改为 part_offset（at）与 header（header）两个字段；serial 断言改为 slot1 serial > slot0 serial，并记录实际值；selftest 样例更新为真实输出。修复后 selftest OK，会话 2 的 12/12 info 断言与 8/8 load 断言全部通过。
- 结论：这是验收工具的缺陷，不是 A3 固件的问题。

### 5.2 主机路由陷阱（两次会话都遇到，已修复）

- 现象：设备断电/上电后 NetworkManager 掉直连，192.168.1.1 被解析为 via 192.168.5.1（用户家庭网的另一台设备），SSH 22 拒绝；会话 1 的 in-session health 因此 FAIL。
- 修复：先手工 nmcli device connect enp0s20u1u4u2c2 恢复直连，health 全绿；随后在驱动 finally 与 health 脚本中都加入路由自愈（检测 via 则重连 USB 网卡，最多等 30 s）。会话 2 中自动生效，results 里 route_fix.action = nmcli-connect-enp0s20u1u4u2c2。

### 5.3 vendor 控制台无 crc32 命令

- vendor U-Boot 2013.04 不认识 crc32（Unknown command）。A3 镜像内的 crc32 可用（crc32 0x43000000 0x100 -> 660a59e8）。
- 装载完整性改以 md.b 全镜像逐块比对为准（448,072 B，0 差异），crc32 不可用时驱动记录 crc32_skipped 而非失败（会话 2 的判定不再依赖 vendor crc32）。

### 5.4 reset no-op（SoC 限制）

- A3 镜像有 reset 命令，但本 SoC 的 A1 端口没有 reset 控制器；执行后打印 reset: the A1 port has no reset controller, power-cycle the board 并停住。
- 因此每次会话的 transition/recovery 都需要一次用户断电；A3 两次会话共 4 次断电（各 2 次）。这一点已在 Lead 裁定中固化到后续 RAM 链会话计划。

### 5.5 文档偏差

- uboot-port/README.md §5 里写的提示符 E2631> 已过期；A3 .config 的 CONFIG_SYS_PROMPT 是 =>（会话实测）。建议在 README 的 A3 检查清单中改掉。
- banner token 的判定必须用镜像内嵌的 g8a9d1f7eecfa（post-am commit 短哈希），不能用 commits.env/UBOOT-INFO 里的 tree 哈希 40f52fb4；后续会话/验收脚本不要混用。

## 6. 判定与后续

- 判定：A3 只读验收 PASS；会话 2 全链路 GREEN，会话 1 的 FAIL 已归因为工具/主机侧问题并在会话 2 修复复验。
- 未覆盖（本会话刻意不做）：e2631boot 裸命令走 bootm 真正启动内核（--boot-test 默认关闭，属下一次可写会话/正式启动路径）；env 写入/saveenv（本设计不提供）；mtd 写入/erase（本轮只读）。
- 后续会话注意：serial 会随刷写递增（当前 12），不要写死；banner token 是 commit 短哈希；reset 永远需要断电；health 要在 uptime >60 s 后再判 MT7916/WiFi。
