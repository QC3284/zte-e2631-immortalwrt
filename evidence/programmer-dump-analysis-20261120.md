# 编程器转储初步分析：`zxhn_e2631_full.bin`（2026-11-20）

- **任务**：task-32（编1），对用户编程器导出的 128 MiB 固件做只读结构分析。
- **结论级别**：本文所有数字均为 2026-11-20/21 在本机对文件实测（mmap 只读，未拷贝进仓库）。
- **一句话结论**：**这不是一份有效的整片 flash 转储。** 整个 128 MiB 是**同一个 2,112 字节页**（= 本机 0x800 字节 boot header 块 + 64 字节 spare 区）的**循环旋转/拼接重复**；文件内不存在 secondboot 负载、U-Boot、env、slot、rootfs 等任何其它内容。它不能作为备份、不能用于刷写，也不能用来证明"另一台设备/另一版本固件"。

## 2. 核心发现：全文件 = 单个 2,112 B 页的旋转重复

### 2.1 源页 S

取第 0 单元（2,112 B）作为源页 **S**：

- S[0:2,048] = **本机** `mtd0-bootloader.bin` 的 `[1:2,048]` + 0xFF（逐字节相等；即本机 0x800 boot header 块整体左移 1 字节，末尾补 1 个 0xFF）。
- S[2,048:2,111] = 63×0xFF，S[2,111] = 0x00（该页 spare 区读出值）。
- 头部结构与本机一致：`128s`@15（本机 @16）、`0001ZXIC..`@127、`BOOTROM`@143、`RSA2048`@159、0x04@171、0x61@176；@723..754 有 32 B 伪随机值（本机 offset 724..755，逐字节相同），疑似签名/哈希类字段。

### 2.2 单元的分类（全 63,550 个）

| 类别 | 数量 | 含义 |
|---|---|---|
| **纯旋转** | **62,334**（98.09%） | 单元 = S 的循环旋转（2112 字节窗口），逐字节精确验证 |
| **拼接单元** | **1,215** | 单元 = 相邻两个旋转的"前一个前缀 + 后一个后缀"精确拼接（与"读取指针在组边界推进"的伪影吻合） |
| 未归类 | 1（文件最后 1 个单元） | 边界特例，无后继旋转可比对 |

**全文件不同的 2,112 B 单元内容只有 2,203 种**（同一内容最多重复 62 次）；不同旋转相位 1,057 种。这就是"看似 128 MB 内容其实只有一页信息"的直接证据。

### 2.3 分组与相位推进（"页头拷贝分布"的真实规律）

- 文件恰好可切成 **2,050 组 × 31 个单元**（2,050×31 = 63,550）+ 128 B 补零。31 单元 × 2,112 B = 65,472 B ≈ 64 KiB − 64 B。
- 组内：**30 个单元相同**（纯旋转），**最多 1 个拼接单元**（1,216 组有 1 个拼接单元，834 组没有）。
- 相位推进：设"头部签名字节在该单元内的偏移"为 q，则
  - 第 0 组：q = 15；
  - 第 c 组（1 ≤ c ≤ 1023）：q = 62c + 16（即每 31 单元一组，签名右移 **+62 B**；等价地组内容 = `rotate_left(S, (2112−(62c+1)) mod 2112)`）；
  - **第 1024 组（文件偏移 64 MiB 处）出现一次"相位停走"**：q 与第 1023 组相同（实测 s_1023 = s_1024 = 2045），随后恢复每 +62 B；
  - 实测例：q = 15, 78, 140, 202, 264, 326, ...（组 0..4）。
- 组内 31 个单元复制同内容，说明**输出端在"重复输出同一缓冲"与"推进指针"之间切换**；组边界处的拼接单元是关键痕迹。

### 2.4 与任务卡中 Lead 实测事实的核对

| Lead 观察 | 实测结论 |
|---|---|
| 页几何 2,048+64 = 2,112 | **一致** |
| 头部拷贝"前 128 KB 每页一份，之后稀疏到 ≥3 MB" | **修正**：头部内容其实**每个单元都有**（63,506 个 `128s` / 63,550 单元）；"稀疏"是固定偏移扫描的假象——签名偏移按组 +62 B 漂移，固定槽位只能偶然命中 |
| OOB 全 FF、最后字节 00 | **仅前 31 个单元如此**；全文件 OOB 分类：00×64 共 52,846；其它 10,642；FF×64 共 31；FF×63+00 共 31。因为 OOB 就是旋转窗口的后 64 B，随相位变化 |
| 全文件无 squashfs/UBI/... 魔数 | **一致**（并且原因已定位：文件里根本没有第二页内容） |
| 与 11-15 实机 mtd0-10 不匹配 | **部分不成立**：第 0 单元与本机 mtd0 的 0x800 头块逐字节同源（仅整体移 1 字节）；其余内容确实不匹配，因为文件里没有其它页 |

## 3. 94% 的 0x00 区域是什么？

不是擦除态、不是读参数错误导致的随机数据、也不是加密：

1. 这些 0x00 全部来自源页 S 自身的 0x00 区域——S 的 2,048 B 数据里只有 64 个非零字节，其余为 0；旋转/拼接只改变位置，不改变字节分布。
2. 依据：62,334 个单元逐字节等于 S 的旋转；全文件只有 2,203 种单元内容；任何非 S 的字节都未出现（例如第二页起应出现的 secondboot 代码、U-Boot 头、env 全部为 0 命中）。
3. 若是擦除态，OOB/数据应整体 0xFF（本机 11-15 实测的 mtd 空区就是 FF）；若是加密，字节熵应接近 8 bit/B，而实测 0.53 bit/B 且与单页 S 的分布一致。

## 4. 与 11-15 实机转储的对比与来源推断

- 本机 `mtd0-bootloader.bin`（1 MiB）头 2,048 B = 0x800 头块：`128s`@16、`0001ZXIC`@128、`BOOTROM`@144、`RSA2048`@160；0x800 起为 secondboot 负载（向量表 `b ...`）；0x20,000 起 U-Boot；0xC0,000 起 env。
- 本文件第 0 单元数据 = 上述头块 `[1:2048]` + 0xFF，**同源但整体差 1 字节**；且**无 secondboot 负载、无 U-Boot、无 env**（0 命中）。
- 因此：
  - ❌ 不是本机（也不是任何设备）的整片转储；
  - ❌ 不是 11-15 实机 mtd0-10 的任何一份；
  - ❌ 不是工厂/擦除态（擦除态应为 FF 为主）；
  - ✅ 最可能是**编程器/读取工具只重复读出了同一页（0x800 boot header 所在页）并带缓冲/指针漂移 bug** 所产生的伪影；源页内容与本机 11-15 的头块一致，**倾向于是同一台机器**（若 @724..755 的 32 B 是逐机唯一签名，则可确定同机；无第二台数据无法 100% 排除"固定模板"）。
- 另外：拼接单元 = 相邻旋转的"前缀+后缀"，以及每 31 单元一组的复制模式，是典型的"读缓冲/指针未正确推进"痕迹，而非 flash 内容特征。

## 5. 与 U-逆1（mtd0 逆向）结论的关系

U-逆1 结论：mtd0 的 0x0..0x7FF 是 2,048 B 头块（0x800），`128s`@0x10，secondboot 负载从 0x800 起，U-Boot @0x20000，env @0xC0000。本文件只在第 0 单元复现了这 2,048 B 头块（且移 1 字节），**0x800 之后的任何内容都不存在**。故本文件对 U-逆1 结论不构成反证，也不能扩展其结论。

## 6. 机制假设（需用户提供编程器信息后确认）

最可能的成因（按可能性排序）：

1. **编程器读模式/芯片参数选择错误**：如按"仅读 boot 页/头区"模式、或页大小/列地址设置错误，导致每次都返回同一页；工具内部再以 64 KiB 缓冲为单位反复输出，指针每次只推进 62 B，从而形成旋转/拼接。
2. **工具固件 bug**：组内 31 单元相同、组间相位 +62 B、64 MiB 处一次相位停走（s_1023 = s_1024）都指向"缓冲/指针计数缺陷"，而非芯片行为。
3. 芯片坏块/ECC 失败后回退到"最后一次成功读"的页（也可解释重复，但难解释相位漂移与 64 MiB 异常）。
4. 用户所说的"编程器固件"实际不是整片读出的文件（例如只 dump 了 boot 区或工具生成的占位文件）。

排除项：同型号另一台设备的正常固件（无第二页内容）、擦除态（非 FF 主导）、加密（熵不符）。

## 7. 建议与风险

1. **风险**：不得把该文件当作备份/救援镜像，**不得刷写**（写回只会复制同一页/或直接损坏 boot 区）；也不要据此判断机器固件版本或"另一台设备"信息。
2. **有效转储做法**（需用户确认编程器型号/软件）：
   - 选对芯片型号（SPI NAND，页 2,048+64 B，容量 128 MiB，ECC 设置与主控一致；型号需与 mtd/proc 信息核对）；
   - 用"整片读取/读全部页"模式，确认地址从 0 连续推进到 128 MiB；
   - 读回后自检：offset 0 应为 0x800 头块（`128s`@0x10）；0x800 起应出现 secondboot 负载字节；0x20,000 起 U-Boot；0xC0,000 起 env（`affcec3e`）；slot0 起始 0x?（以实机 mtd 表为准）。
   - 若工具无法整片读，继续使用已在手的 11-15 实机 mtd0-10 转储（其完整性已由 U-逆1 与部署链复验）。
3. **可向用户确认的信息**（影响最终定性）：编程器型号与软件版本、所选芯片型号/页大小/ECC/读模式、读取耗时与是否报错、该文件是否由"读取芯片"直接生成还是经过工具转换。
4. 本文件建议保留但标注为"无效/伪影"，避免后续误用。

## 8. 可复现性与脚本

- 全部脚本在 `/tmp/e2631-dump/`（`recon1.py`..`recon26.py`），均只读 mmap；关键步骤：
  1) 按 2,112 B 分单元，统计字节/字符串直方图；
  2) 以第 0 单元 S 为源，用多锚点（`128s`/`0001ZXIC`/`BOOTROM`/`RSA2048`/@723 随机块）求旋转相位并逐字节比对；
  3) 对非旋转单元，用相邻旋转做"前缀+后缀"精确拼接验证；
  4) 按 31 单元分组统计相位公式与 64 MiB 异常；
