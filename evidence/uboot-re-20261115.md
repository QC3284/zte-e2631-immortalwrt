## 1. 方法与地址换算

- 本机 /usr/bin/objdump（binutils 2.47）**未编入 ARM target**，objdump -m arm 直接报
  "can't use supplied machine arm"；llvm-objdump 23.1.5 可反汇编 ARM 但不接受裸二进制
  （无 -b/--binary-architecture）；aarch64 工具链的 objdump 也不含 arm。
- 实际使用 **capstone 5.0.9**（python3 -m pip install --target /tmp/pylibs capstone，
  运行时 PYTHONPATH=/tmp/pylibs），Cs(CS_ARCH_ARM, CS_MODE_ARM) + skipdata=True。
- 两个镜像带同样的 0x800B 头块，用向量表/字面量池反推加载基址后得到换算关系：

```
secondboot: 运行时地址 = 0x00200000 + 文件偏移          （代码从 file 0x800 起）
U-Boot    : 运行时地址 = 0x47F00000 + (文件偏移 - 0x20800)（代码从 file 0x20800 起）
```

- 逆向脚本只写 /tmp（/tmp/dis_*.txt 等），不随本文件入库。

### 2.1 0x800B 头块格式（两个镜像一致）

非零字节分布（file 0x0 起）：

```
+0x010  4B  "128s"                 ← ROM/secondboot 认的魔数
+0x014  4B  LE 载荷长度            secondboot=0x00008000，U-Boot=0x00068000
+0x080  10B "0001ZXIC.."
+0x090   7B "BOOTROM"
+0x0A0   7B "RSA2048"
+0x0AC  4B  LE 0x00000004
+0x0B0  4B  LE 0x00006100(secondboot) / 0x00066080(U-Boot)
+0x2D4  32B 每镜像不同的 32B 值（用途未定，见 §10）
其余 0x800B 内为 0x00
```

注意：头块不是 64B，而是 0x800B；长度字段不计头块（载荷从 +0x800 开始）。
0x2D4 的 32B 值在 secondboot 为 aa19ebce...1ec4726、U-Boot 为 4cd57592...2ed009，
本报告尝试的常见 SHA-256 区间组合均未命中，暂按"签名/摘要/密钥类数据"存疑处理。

### 2.2 64B 描述块（载荷尾部 trailer）

0x86800 与 0x88800 各有一份，布局相同（0x40B）：

```
+0x00 16B  aa aa aa aa 55 55 55 55 44 44 44 44 99 99 99 99
+0x10 16B  "V1.0.0" + 9x00 + 0xFF
+0x20  1B  0xFF
+0x21 19B  "2023-08-28 19:11:33"（第一份）/ "2023-08-28 19:11:52"（第二份）
+0x34  4B  0x00066040（第一份）/ 0x088840（第二份）  ← 基准不一致，见 §10
+0x38  4B  0x00000000
+0x3C  4B  0x00100000
```

第一份位于载荷内偏移 0x66000，其 +0x34 = 0x66040 恰为"该描述块结束位置相对载荷起点"；
第二份位于载荷正常结束处（0x20800+0x68000=0x88800），+0x34 = 0x88840 为文件绝对值。
两份都是打包器留下的，secondboot 只读取第二份（见 §3）。

## 3. Q1："backup header!!" 的精确语义

### 3.1 字符串与唯一交叉引用

- 字符串 "backup header!!\n" 位于 file **0x61D5**（运行时 0x2061D5）。
- 整个 secondboot 代码中对该字符串**只有一个引用**：0x205944 的
  ldr r0, [pc, #0x4c]，取池 0x205998 处的字面量 0x2061D5，随后 bl 0x204DF8 打印。

### 3.2 打印点的上下文（F_verify @0x2058D4）

```
002058d4: push  {r3, r4, r5, r6, fp, ip, lr, pc}
002058e0: mov   r5, r0              ; r5 = 镜像头指针（RAM 0x47800000）
002058e4: bl    #0x2057d0           ; 读安全启动 strap，返回 0/1
002058e8: ldr   r6, [pc, #0x94]     ; r6 = 0x73383231 ("128s")
002058ec: subs  r4, r0, #0
002058f0: bne   #0x205918           ; strap=1 -> secure 路径
002058f4: ldr   r0, [pc, #0x8c]     ; "non secure uboot \n"（0x2061B4）
002058f8: bl    #0x204df8           ; 打印

00205904: beq   #0x205930           ; 相等 -> non-secure 交接
00205908: ldr   r0, [pc, #0x7c]     ; "chip id err!\n"（0x2061C7）
```

secure 路径（本机未走）：0x205964 起先 bl 0x2053A8 做 RSA/SHA 类校验，

### 3.3 备份动作（F_205800 @0x205800）

```
00205814: ldr   r2, [pc, #0x9c]     ; 0xAAAAAAAA
00205818: add   r1, r3, #0x47000000
00205820: ldr   r3, [pc, #0x98]     ; 0x47F00000

0020582c: ldr   lr, [pc, #0x94]     ; 0x99999999
00205830: cmp   r1, r3              ; 边界：不越过载荷起点
00205834: bls   #0x205880
00205838: ldr   r5, [r1]            ; 依次比较 4 个字：

...
00205880: mov   r1, #0
00205884: mov   r2, #0x800
00205888: ldr   r0, [pc, #0x40]     ; 0x40080000

00205894: mov   r2, #0x800
00205898: ldr   r0, [pc, #0x30]     ; 0x40080000
```

字面量池 0x2058B8-0x2058D0 依次为：0xAAAAAAAA、0x55555555、0x47F00000、

即：在 0x47F00000 + len 处向下按 16B 步长找 16B 魔数；命中则把紧随其后的 64B
复制到 0x40081000；无论是否命中，都把 0x800B 镜像头复制到 0x40080000，并把
原位置的 0x800B 清零，然后返回继续跳转。

### 3.4 串口互证

board/ser-final.log 第 16-18 行：

```
16 non secure uboot
17 backup header!!
18 Jump
```

同样的三行在 ser-hbcheck.log:39/40、ser-newimg.log:17/18、ser-newslot.log:17/18、
ser-reflash.log:17/18、ser-wifi.log:17/18 都出现（每次正常启动都有），排除了
"这是异常/回退分支"的可能。

### 3.5 结论与推断

- **语义**：这是"跳转前备份镜像头"动作的提示行，不是"使用 backup header"。
- 动作顺序：memcpy 载荷到 0x47F00000 → 打印 backup header!! → 备份头到 0x40080000、
  尾部 64B 到 0x40081000、清零原头 → 打印 Jump → 跳 0x47F00000。
- **推断（非实证）**：0x40080000/0x40081000 是留给后续阶段/调试模式的固定 RAM 副本；
  本次对整份 mtd0 做 4 字节对齐字面量搜索，0x40080000 只被 F_205800 自己引用一次、
  0x40081000 同样只在 F_205800 的池里出现一次，说明这份备份在 mtd0 范围内**没有消费者**
  ——消费者可能在 ROM 的调试模式或外部工具里，也可能当前固件根本不再读取（低风险）。
- **重要**：尾部 64B 描述块**不是启动必需**——找不到魔数时 F_205800 仍然照常备份头并返回，
  随后照常跳转。自定义 U-Boot 不带 trailer 也能启动（只是 0x40081000 不被填）。

## 4. Q2：跳转 U-Boot 之前到底检查了什么

### 4.1 安全启动 strap（@0x2057D0）

```
002057d0: push  {fp, ip, lr, pc}
002057dc: ldr   r2, [pc, #0x18]     ; 0x9A107000
002057e0: ldr   r3, [r2, #0x40]     ; 轮询 [0x9A107040] 直到非 0
002057e4: cmp   r3, #0
002057e8: beq   #0x2057e0
002057ec: ldr   r3, [pc, #8]        ; 0x9A107000
002057f0: ldr   r0, [r3, #0x1c]     ; 读 [0x9A10701C]
002057f4: and   r0, r0, #1
002057f8: ldm   sp, {fp, sp, pc}    ; 返回 bit0
```

### 4.2 校验结论（本机走 non-secure 分支）

1. strap bit0 = 1 → 打印 "secure uboot "，调 0x2053A8 做加密校验（本机未走，细节未逆）；
2. strap bit0 = 0 → 打印 "non secure uboot "，只做 **一个 32 位比较**：
   镜像头 +0x10 是否等于 0x73383231（"128s"）；不等 → 打印 "chip id err!" 返回失败；
3. 相等 → 直接把头后 0x800 处的 [头+0x14] 字节 memcpy 到 0x47F00000，然后备份头 + 跳转。

**non-secure 分支不存在任何 CRC、哈希、签名或长度上界检查**；[头+0x14] 的值只用来决定
memcpy 长度和尾部 64B 扫描起点。换句话说：只要头块里写对 "128s" 和一个长度，
payload 内容可以是任意字节，secondboot 都会照拷照跳（长度过大可能导致 RAM 越界，
属于可被恶意镜像利用的点，但自用场景下不是问题）。

### 4.3 调用链：三条读镜像路径最终都汇到 F_verify

启动源分派函数 @0x201F94 读取 [0x94000040] 的 bit[7:6]：

```
00201fa0: mov   r3, #0x94000000
00201fa4: ldr   r3, [r3, #0x40]
00201fa8: ubfx  r3, r3, #6, #2
00201fac: cmp   r3, #2  -> 打印 "SPI NOR\n"  (0x205CCB) -> bl 0x20283C
00201fb4: cmp   r3, #3  -> 打印 "SPI NAND\n" (0x205CD4) -> bl 0x202C68
00201fbc: cmp   r3, #1  -> 打印 "NAND\n"     (0x205CD8) -> bl 0x202544
```

三条路径结构相同：从 flash 偏移 **0x20000** 读 **0x100000** 字节到 RAM **0x47800000**
（读失败直接返回；成功则把 r0=0x47800000 交给 F_verify）：

- SPI NOR：读封装 0x2027F4，包装函数 0x20283C；
- SPI NAND：读封装 0x202B2C，包装函数 0x202C68（tail b 0x2058D4）；
- 另一条：读封装 0x2022F8，包装函数 0x202544（同样 tail b 0x2058D4）；
- F_verify 还有第三个入口 0x202574（同样 b 0x2058D4）。

串口实测本机走的是 SPI NAND 分支：ser-final.log:15 打印 "SPI NAND"，紧接着
16/17 行就是 F_verify 的 "non secure uboot / backup header!!"，与反汇编完全对应。

### 4.4 对文档原结论的纠正

原文档 "§2 128s 逐字符比对代码 @0x5984（ldrb/cmp #0x34）" 是把两段不同的东西混在一起：

- file 0x5984 是**字面量池里的数据**（0x73383231），被 F_verify 的 ldr r6,[pc,#0x94] 取用；
- ldrb r3,[r0,#0xa6]; cmp #0x34 / #0x36 位于函数 0x20537C，是**芯片型号/参数分派**
  （'4'→返回 0x400，'6'→0x600，其它→0x800），与 "128s" 无关。

真正的魔数检查是 4.2 里的 32 位 cmp。

## 5. Q3：env 区头 4B 的 CRC

### 5.1 读取与校验链

```
readenv @0x47F0C0AC:
  sub sp, sp, #0x20000 ; 128KB 缓冲
  sub sp, sp, #0x40
  mov r0, #0xC0000     ; flash 绝对偏移
  bl  0x47F0C05C       ; env 驱动读（长度取全局 env 大小，封顶 0x20000）
  cmp r0, #0
  bne  "!readenv() failed"
  mov r0, buf
  mov r1, #1
  bl  0x47F0B61C       ; env_import(buf, 1)

env_import @0x47F0B61C:
  memcpy(local, buf, 4)              ; 取头 4B 作为"存储的 CRC"
  mov r0, #0
  add r1, buf, #4                    ; 数据从 +4 开始
  ldr r2, [pc, #0x88]                ; 常量 0x1FFFC
  bl  0x47F23334                     ; crc32(0, data+4, 0x1FFFC)
  cmp r0, [local]                    ; 与存储值比较
  beq ok
  -> "!bad CRC" 分支
```

### 5.2 数值验证

```

calc   = zlib.crc32(d[0xC0004:0xC0004+0x1FFFC]) & 0xffffffff
print(hex(stored), hex(calc), stored == calc)
EOF
0xaffcec3e 0xaffcec3e True
```

### 5.3 结论

- env 区= **128KB**（0xC0000-0xDFFFF，长度常量 0x1FFFC = 0x20000-4 自洽）；
- 校验算法= **标准 CRC-32（IEEE 802.3，反射多项式 0xEDB88320、初值 0xFFFFFFFF、
  末尾取反）**，与 zlib.crc32 / U-Boot 自带 crc32 结果一致；文件里存的是小端 4B；
- 原文档"任何标准窗口都不匹配"是因为按 64KB/其它窗口试算；正确窗口是 data[4:0x20000]。
- 运维含义：任何工具重写 env 时必须重算这个 CRC 再写回，否则 U-Boot 会走 "!bad CRC"
  回落到默认 env（bootcmd 等全丢）。
- 旁注：U-Boot 里另有 csp_crc/固件头 CRC（字符串 "header crc error! cur calc:0x%x,
  HeaderCrc:0x%x"），是另一套（非反射 CRC32，多项式 0x04C11DB7），不要与 env CRC 混淆。

### 6.2 摘要位置与数值验证

- 存储摘要位于运行时 0x47F41780 = file **0x61F80**，20 字节：
  69 f0 d9 fc fa 79 a3 21 a2 b4 ff 96 23 9f e5 88 6b dc 99 a3；
- 相邻 0x47F41794 = file 0x61F94 处的 u32 = 0x00000001，即"启用密码保护"标志；
- 验证：

```
hashlib.sha1(b"5cE080@fyBD").digest().hex()
 -> 69f0d9fcfa79a321a2b4ff96239fe5886bdc99a3  （与 file 0x61F80 完全一致）
```

### 6.3 结论

- 机制= **无盐 SHA1(ASCII 密码) 与镜像内嵌 20B 摘要做 memcmp**；明文不存于任何分区，
  所以整份 dump 里搜不到 "5cE080@fyBD" 这类字符串——不是被混淆，而是根本没存；
- 密码最长 16 字符（已知口令 12），输入回显 '*'，成功后只清 RAM 标志，不写 flash；
- 安全含义：这属于"防误入 bootmode 菜单"的操作性门槛，不是密码学保护。任何能改
  U-Boot 镜像的人都可以把 file 0x61F94 的 u32 改成 0 或换掉摘要来绕过。

## 7. Q5：两段全零区到底意味着什么

### 7.1 全镜像 '128s' 出现位置（逐字节搜索）

```
0x00010   secondboot 镜像头魔数（真头）
0x020010  U-Boot 镜像头魔数（真头）
0x05984   secondboot 代码里的字面量池数据（F_verify 用，非头）
0x4EDF8   U-Boot 代码内嵌的 4 字节（对齐）
0x4F4B4   U-Boot 代码内嵌的 4 字节（对齐）
0x5FC2F   板名 "Board: ZTE zx279128sevb" 字符串内的巧合子串
```

即：**不存在第三份镜像头**，0x10000 处没有可被当作 secondboot 备份的 "128s" 头。

### 7.2 0x10000-0x1FFFF

- 128KB 引导槽 0x0-0x1FFFF：头块 0x800B + 载荷窗口 0x8000（0x800-0x87FF）；
- 实际代码只到 0x68AB，0x68AC-0x87FF 是窗口内 0 填充，0x8800-0x1FFFF 是槽尾 0 填充；
- 该槽之后下一个 128KB 边界 0x20000 立即是 U-Boot 头块 —— 说明 ROM/secondboot 的布局
  就是"0x0 起 128KB 给 secondboot，0x20000 起给 U-Boot"。
- 0x10000 全零只是这个 128KB 槽没被用满的尾部，不是刻意备份/历史镜像。

### 7.3 0xD0000-0xDFFFF

- env 区是 128KB（0xC0000-0xDFFFF），CRC 覆盖 0x1FFFC 字节，其中 env 文本只到 0xC021E，
  其后全部是数据区的 0 填充；
- 0xD0000 正好是这 128KB 的后半段起点，所以全零。**不存在第二个 env CRC 扇区**
  （若是独立备份，头部应有自己的 4B CRC，实测没有）。

### 7.4 关于"0 而不是 0xFF"

这两个区域是 0x00 而不是擦除态 0xFF，说明它们是被当作镜像数据显式写入的（厂商按 1MB
整块烧写／或 dump 工具按 0 补齐），而不是"从未写入的擦除区"。全镜像中真正的擦除态
（0xFF）只有 0x88840-0xBFFFF 与 0xE0000-0xFFFFF 两段。物理层原因未在硬件上验证。

## 8. 对自定义 U-Boot 的工程含义（给后续任务的输入）

1. **写入位置**：U-Boot 镜像必须放在 mtd0 偏移 **0x20000**；secondboot 固定从该偏移读 1MB
   到 0x47800000，再看头块 [+0x14] 长度。
2. **头块**：最稳妥是沿用当前 U-Boot 头块（0x800B）逐字节，只改 +0x14 为新 payload 长度；
   +0x10 必须保持 "128s"。0xB0 等字段用途未定，建议先把原值抄过去。
3. **长度上限**：payload 长度不能侵入 env 区，即 0x20800 + len <= 0xC0000，
   len <= **0x9F800（约 638KB）**；当前 U-Boot payload 为 0x68000（416KB），后续擦除态
   可用空间约 222KB（0x88840-0xBFFFF）。
4. **无完整性校验**：non-secure 分支不校验 payload 的 CRC/签名，坏镜像 secondboot 不会拦。
   刷写实验必须保留 TFTP 救砖通道（env 里 bootfile/linuzfile/loadaddr + bootm 现成可用），
   并且优先在串口在线时操作。
5. **尾部 64B 可选**：保留时放 0x20800 + len 处，内容按 §2.2；不保留也能启动。
6. **env 不要动**；若要改，必须按 §5 重算 128KB 区的 CRC。
7. **不要动 0x0-0x1FFFF 的 secondboot**：ROM→secondboot 这一段本次未逆（见 §10），
   保持原厂可以把风险限制在 U-Boot 一段。
8. **验证信号**：串口应看到 non secure uboot → backup header!! → Jump → U-Boot 横幅。

## 10. 未解决 / 低置信度项

1. 头块 +0x2D4 的 32B 值：两个镜像不同，尝试 SHA-256(常见区间组合)未命中；用途未定
