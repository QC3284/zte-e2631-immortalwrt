## 0. 结论摘要

**会话结论：RED。** F2（U-Boot 以太网 DHCP/PING/TFTP）继续失败，但本次拿到了决定性证据；F1（e2631boot → 内核交接）在本产物上的失败签名与 2026-11-22 不同。

1. **F2 决定性证据：物理线上零帧。** 设备侧 `dhcp` 打印了 6 轮 × 7 次、共 42 次 `BOOTP broadcast`（257.51 s 无地址），`ping`/`tftp` 全部 ARP Retry 失败；同期主机 `tcpdump`（enp0s20u1u4u2c2，66 帧）里来自 U-Boot MAC `00:41:71:00:00:50` 的帧 **0 个**，BOOTP/DHCP 行 **0 条**，主机 dnsmasq 也没有任何 DHCP 事务记录。抓到的唯一设备帧是重启前的 SSH（设备 LAN MAC，10:48:45 UTC 之前）。=> 帧没有离开芯片，问题在 U-Boot 发送路径/更底层（BMU/DMA/交换机端口启动），不是主机、不是抓包位置。

3. **F1 失败签名（本产物）：镜像对 bootm 不可见。** `e2631boot load` 打印 `header and data CRCs are good`，但紧接着 `md.l 0x42000000 8` 只看到 slot 标记（`33333333 …`）、`md.l 0x420020 8` 全 0；`iminfo 0x420020` = `Unknown image format!`；`bootm 0x42000000` / `bootm 0x420020` / `bootm start 0x42000000` 均为 `Wrong Image Type for bootm command` + `ERROR -91: can not get kernel image!`；无 `Bad Magic`、无 abort、无 `Starting kernel`。这与 2026-11-22 20-patch 产物上的「静默返回」（bootm 已打印 uImage 名/尺寸/CRC/load，之后才返回提示符）**不是同一签名**。
4. **待复现观察（本会话不作解释）：** 同一段 DRAM（0x42000000 / 0x43000000 / 0x48000000 区域）在 `md`（按字读）与 `crc32`/`iminfo`/`bootm`（按块读）之间出现可见性不一致，且数据会在命令之间出现/消失；已用 5 轮只读探针定位到大致的边界（0x4A000000/0x4C000000 的 mw+md 正常、0x47F00000 的 crc32 与主机重算一致、0x4B000000 的 32 字节标记 crc32 正常）。按 Lead 裁定：只记录观察、串口原始字节入库、thin 会话复现。

1. 本次证据把 F2 从「DHCP 拿不到地址」收紧为「**没有帧上线**」：设备侧打印 `BOOTP broadcast` 但物理口无帧。

### 4.3 源码路径（为什么是这两个错误行）

- `boot/bootm.c:349-358`：`boot_get_kernel` 返回 `-EPROTOTYPE` 时打印 `Wrong Image Type for %s command`；`bootm` 主命令随后打印 `ERROR -91: can not get kernel image!`。
- `boot/bootm.c:266-268`（`boot_get_kernel` 的默认分支）：`genimg_get_format(buf)` 既不是 LEGACY 也不是 FIT/ANDROID 时返回 `-EPROTOTYPE`。
- `Bad Magic` 只在 `boot/bootm.c:76` 与 `boot/image-board.c:50` 出现；本次没有，说明 U-Boot 读到的是 0 而不是错误的魔数。
- `e2631boot` 侧：`board/zte/zxhn-e2631/e2631boot.c:198 e2631_load_kernel()` 先读 slot 标记 + 版本头做校验，再 `mtd_read` 整个 uImage（0x20 + 3,491,146 B）到 `CONFIG_SYS_LOAD_ADDR`（0x42000000），最后对 `addr+0x20` 做 `image_check_dcrc`；`load` 子命令在打印 CRCs good 后返回 `CMD_RET_SUCCESS`，不 boot。

注意：`758d6336` 正是 **64 个 0 字节的 CRC32**（本地重算），所以 crc32 也认为该区域全 0；而 `md` 在 0x43000000/0x42000000 处能看到标记。也就是说这不是「iminfo/bootm 单独读错」，md 与 crc32 在两个地址上同时分成两种视图。

## 5. 补充观察：DRAM 区域的 md vs crc32/iminfo/bootm 可见性不一致（待复现，不作解释）

### 5.3 观察到的事实与边界

- 同一地址的可见性会在命令之间变化：ramtest2 里 `md` 看到数据而 `crc32` 看到 0；ramtest3 里 `crc32` 看到 0 而随后的 `md` 看到数据；之后又都变成 0。
- 不是「md 一律正确」：`md 0x490020`、`md 0x420020` 也读到 0（mw 写过的范围内也出现 0）。
- 不是「crc32 坏了」：0x47F00000、0x4B000000 的 crc32 与主机重算完全一致。
- 不是「e2631boot load 会把任意 RAM 清零」：ramtest5 的 0x4C000000 图案在 load 后仍在。
- 数据消失现象集中在 0x42000000 / 0x48000000 / 0x43000000 这些会被 e2631boot / mtd read 写入的低地址段（本次样本），0x4A000000/0x4B000000/0x4C000000 的显式写入读回正常。
- **不能排除串口/hub 假象**：所有输出都经 serialhub（single-reader）解析为 JSON 再由驱动记录；本目录同时保留串口原始字节（`serial-run1.txt`、`serial-f1diag.txt`、`serial-ramtest*.txt`），原始字节里上述行确实存在（`cat -v` 可复验），但「某条输出属于哪次命令」的归属仍受 hub 读取时序影响。
- 本会话按 Lead 裁定**不下结论**；复现步骤见 §8.2。
