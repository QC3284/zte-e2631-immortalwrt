## 2. 本地验证（重放确定性）

在 uboot-src 的本地克隆里把 kit 的 22 个 patch 用新参数重放两次：

| 项 | run 1 | run 2 |
| --- | --- | --- |
| `HEAD` | `f355ce89283cf584e9c431d5c707aea6077667c4` | 相同 |
| `HEAD^{tree}` | `c812dd8689ccf146deeec83bd0e74067c8b8abc5` | 相同（= pin） |

因此理论上 banner token 应为 `gf355ce89283c`、构建时间为固定的 `Nov 19 2026 - 15:44:39 +0000`；
CI 两次 run 与预测完全一致（见 §3）。

为什么之前不可复现：

1. U-Boot 版本串含 `git describe` 的 HEAD token；CI 用 `git am` 现场重放，默认 committer date = 构建时刻，
   所以每次 HEAD SHA 都不同；
2. `include/generated/timestamp_autogenerated.h` 在编译期嵌入 `U_BOOT_DATE`/`U_BOOT_TIME`；
   未设 `SOURCE_DATE_EPOCH` 时取构建时钟。

实测（run `44982672016` vs `44983615483`，同一 tree）：两份 `u-boot.bin` 只差 **28 个字节**，全部是这两处
版本/时间字符串（见 [uboot-checkpatch-maintainers-20261122.md](uboot-checkpatch-maintainers-20261122.md) §4）。

## 5. 边界与重验

- 可复现性的前提：同一 runner 镜像/toolchain（ubuntu-24.04 + apt 的 arm-none-eabi-gcc）与相同 pin。
  runner 镜像或工具链版本变化会改变 `.config`/编译结果，需重新记录基准（这是环境变化，不是 pin 漂移）。
- 重验方法：同一 head 连续 dispatch 两次，各自下载 artifact 后 `cmp` `u-boot.bin` 与 mtd0；
  或直接比较 `UBOOT-INFO.txt` 的 `Banner`/sha256/crc32。
- `SOURCE_DATE_EPOCH` 只影响 banner 时间（以及 fit-dtb.blob 的 mtime touch），不改变任何功能代码。
- 若将来升级 pinned base commit，`E2631_UBOOT_SOURCE_DATE_EPOCH` 可保持冻结（推荐）或改为新 base 的
  committer 时间——两者都固定，只需在 evidence/README 同步新 banner。
