# P2-C1a：A3 U-Boot bootm 干跑（预闪写门禁）— 2026-11-21

## 0. 结论（RED）

C1a 的结论是 **RED：A3 U-Boot 无法启动生产内核。在修复前不得进入 C1b（写 mtd0）。**

- 我们的 A3 U-Boot 从 RAM 正常跑起来了：banner `U-Boot 2027.01-rc2-g8a9d1f7eecfa`，
  `e2631boot` 正确选中 slot1（serial 12 > slot0 serial 7），uImage 装载与 CRC 校验全部通过；
- `bootm` 在进入内核之前、构造 ATAGS 时发生 **data abort**（`boot_prep_linux + 0x74`），
  随后落到我们的 `reset`（A1 无复位控制器、no-op），设备停在 U-Boot 提示符；
- 根因：移植板级代码从未初始化 `gd->bd->bi_boot_params`（全树无赋值），ATAGS 缓冲区
  指针不是合法 DRAM 地址，第二个 tag（ATAG_MEM）写入时 data abort。A3 验收此前只做
  `info` / `load`，从未真正执行 `bootm`，所以这是潜伏至今的 pre-flash blocker；
- 全程 **零 flash 写入**：会话没有发送任何写命令；用户断电重启回 stock 链后，
  `/dev/mtd0` 的 sha256 与 C1a 之前完全一致（`887a7f6c…0fa9f`），设备健康正常；
- 驱动的“Linux 标记”判定有一个假阳性缺陷（把 uImage 名称里的 `ImmortalWrt` 当成用户态标记），
  已修正；不影响本次结论（abort 是真实发生的）。

## 5. 故障细节与根因

串口原文（`a3-boot-continuation-002.txt` 摘录）：

```

e2631boot: header and data CRCs are good
## Booting kernel from Legacy Image at 42000020 ...
   Image Name:   ARM ImmortalWrt Linux-6.18.60
   Image Type:   ARM Linux Kernel Image (uncompressed)
   Data Size:    3491050 Bytes = 3.3 MiB
   Entry Point:  40008000
   Verifying Checksum ... OK
Working FDT set to 0
   Loading Kernel Image to 40008000
data abort
pc : [<4ff9578c>]      lr : [<4ffd6edc>]

resetting ...
reset: the A1 port has no reset controller, power-cycle the board
```

定位：

- `reloc pc 0x4300178c` 对应 link 地址 `0x4300178c`，在 `u-boot.map` 中属于
  `.text.boot_prep_linux`（0x43001718 + 0x74）；调用者是 ARM 通用 `bootm` 的
  `arch/arm/lib/bootm.c` `boot_prep_linux()`，不是我们的 `e2631boot` 代码；
- 出错指令 `e5810004` = `str r0, [r1, #4]`；`r0=0x54410002` 正是 `ATAG_MEM`，
  `r1=0x967fc480` 在 DRAM 窗口（0x40000000–0x4fffffff）之外，写入即 data abort；
- A3 的 .config 只开了 `CONFIG_SETUP_MEMORY_TAGS=y`（CMDLINE/SERIAL/REVISION/INITRD
  tag 全部关闭），所以 ATAGS 路径只产生 ATAG_CORE + ATAG_MEM；
- `setup_start_tag()` 从 `bd->bi_boot_params` 取 ATAGS 缓冲区地址（`arch/arm/lib/bootm.c:47`，
  另一处读取在 `:336`）。对 post-am tree `40f52fb4` 全树 grep：**没有任何一处给本板赋值**
  `bi_boot_params`；`board/zte/zxhn-e2631/zxhn-e2631.c` 只有 `dram_init` /
  `dram_init_banksize` / `reset_cpu`；`bd_info` 在 `common/board_f.c` 的 `reserve_board()`
  里被清零，因此该字段从未被放进合法 DRAM 地址；
- A1/A2/A3 验收只做 `info` / `load`，从未执行 `bootm`，所以这个缺陷一直潜伏到 C1a 才暴露。

修复方向（属于 U-Boot 移植，见 board task-53）：

- 在板级初始化（`board_init`/`board_late_init`，必须早于 `bootm`）设置
  `gd->bd->bi_boot_params = CFG_SYS_SDRAM_BASE + 0x100;`（DRAM base 0x40000000），
  并确认该 ATAGS 区域不与内核 load/entry（0x40008000）、U-Boot 自身（0x4ff…）冲突；
- 重新构建 A3/A4，重跑 C1a（仍然零 flash 写入）通过后才可讨论 C1b。

## 8. 驱动缺陷与修正

本次驱动 `/home/qc233/zte/e2631-p3/c1a_bootm.py` 有一个监视器缺陷：`LINUX_MARKERS`
里包含了 `ImmortalWrt`，而 uImage 名称与 slot1 版本字符串都含该词，监视器在
“e2631boot: slot1 ... version ImmortalWrt v1.10.0”这一行就误判为 Linux 已起来，
提前结束监视并停止 serialhub，导致后续 bootm/abort 由恢复后的捕获链记录。
修正内容：

- `LINUX_MARKERS` 只保留 `e2631-wifi-boot`、`automatic Wi-Fi initialization complete`、
  `Please press Enter`、`login:`；
- `PANIC_PATTERNS` 增加 `data abort`、`prefetch abort`、`undefined instruction`，
  使 bootm 阶段异常直接判定 RED 并保留完整 tail；
- 下一次 C1a 重跑会使用修正后的驱动，串口从 `go` 到内核/异常全程由同一 reader 记录。

### 11.3 C1a 重跑清单（零 flash 写入）

2. `go 0x43000000`，此后驱动只读串口。
3. 预期串口顺序（关键判据）：
   - `U-Boot 2027.01-rc2-g…` banner；
