### 3.1 U-Boot 区界核对（用 P0 工具 `tools/lib/mtd0.mjs` 解析）

- 头部在 0x20000，payload 偏移 `PAYLOAD_OFF = 0x20800`（0x20000 + 0x800）；
- `declaredLen = 0x68000`，payload 结束于 0x88800，未超过 `PAYLOAD_MAX = 0x9F800`，也远在 `ENV_OFF = 0xC0000` 之前；
- 0x88800..0x88840 这 64 B **不是保留区也不是 FF**（见 §3.2），0x88840..0xC0000 全是 FF（擦除态）；
- 结论：Lead 修正的写区界 0x20000..0xC0000 与实测一致；镜像实际内容边界是 0x88840，env 起始 0xC0000 不变。

### 3.2 头部、payload 尾标与 env

- U-Boot head block（0x20000 起）：+0x10 处 ASCII “128s”；+0x14 是 LE u32 payload 长度 0x00068000；
  +0x80 “0001ZXIC..”，+0x90 “BOOTROM”，+0xA0 “RSA2048”，+0xAC = 4，+0xB0 = 0x00066080；
  +0x2D4 起 32 B digest = `4cd57592279d47408f91b6c38610fe92d79268b3ec64fefbbfe87bffe52ed009`。
- payload 尾部 0x88800 起 64 B（非 FF，63/64 字节非 0xFF）明显是厂商 trailer：
  开头 8 个 32-bit 魔数样式的 `aaaaaaaa 55555555 44444444 99999999`，随后 ASCII “V1.0.0”、0xFF、
  “2023-08-28 19:11:52”，再往后是 `40 88 08 00`（=0x00088840，疑似镜像总长）与 `10 00 00 00`。
  这一结构不属于 OOB 任务，但说明 **0x88800 之后到 0xC0000 之间是空的，重打包时不要动 trailer**；
  建议 A3 移植任务（task-43）把它纳入 U-Boot 镜像格式核对。
- env 位于 0xC0000：首 4 B = `3e ec fc af`（LE CRC32 = 0xAFFCEC3E）；`envParse` 解析出 22 项且
  `crcOk=true`、`envEncode` 往返逐字节一致（`envEncode roundtrip=true`）；键集合与 P0 记录一致。

## 4. OOB 读取结果

### 4.1 正常模式（ECC 开启，MTD_OPS_PLACE_OOB）

- 512 页 × 64 B = 32,768 B，输出 sha256 `2d864c0b789a43214eee8524d3182075125e5ca2cd527f3582ec87ffd94076bc`；
- 非 0xFF 字节数 = **0**（逐字节统计）；逐页表见 `evidence/p2-oob/mtd0-oob-512x64-20261121.hex`
  （2 行注释 + 512 行 page/offset/64 B hex）。

### 4.2 RAW 模式（MTDFILEMODE 关 ECC 引擎）

- RAW 模式常量取 mtd-utils 头文件：`#define MTDFILEMODE _IO(M, 19)` = **0x4D13**；
  枚举 `MTD_FILE_MODE_NORMAL=0, OTP_FACTORY=1, OTP_USER=2, RAW=3`。
  （首次误用 `_IO(M,13)=0x4D0D`，设备返回 ENOTTY/errno 25，已纠正。）
- 工具输出 “MTDFILEMODE set to MTD_FILE_MODE_RAW (ECC engine disabled for this fd)”；
- 512 页 RAW OOB sha256 **同为** `2d864c0b…`，`raw == normal` 逐字节相同，仍全部 0xFF。
- 结论：在本内核/本芯片上，“关 ECC 引擎”不影响用户态读到的 spare 字节。

### 4.3 跨分区对照（关键证据）

对 mtd5 slot0、mtd7 rootfs、mtd8 rootfs_data、mtd10 userdata 各读 4 页 OOB，normal 与 raw 各一次：

| 分区 | OOB normal sha256 | OOB raw sha256 | 主数据页 0 sha256 |
| --- | --- | --- | --- |
| mtd5 slot0 | `3d6876a0…` | `3d6876a0…` | `a7fbdda32a04d357942a7b00f4622a897fb498de2b0e7bd19ae5eb5ff09630be` |
| mtd7 rootfs | `3d6876a0…` | `3d6876a0…` | `aebdb4b5f06304842ffb99304bd769b3d0229e20c2687356a8014f0870bae188` |
| mtd8 rootfs_data | `3d6876a0…` | `3d6876a0…` | （4 页全 FF，见日志） |
| mtd10 userdata | `3d6876a0…` | `3d6876a0…` | `d32886b39ccd1098d69e056b5093a62c34f663483da7a4fdb2cab49551a8e176` |

（4 分区 4 页 OOB 合并 sha256 均为 `3d6876a0146de8576eb2395a858de1213d1b92c65b779df3a331cfd5a4584546`，全 FF。）

对照主数据：mtd7/mtd5/mtd10 的页 0 都有真实内容，mtd0 主数据 338/512 页非 FF，说明引导区确已写入；
但在这些已写入的分区上，OOB 仍一律返回 FF。**因此全 FF 不是 mtd0 的特例，也不代表 OOB 物理为空**，
而是本读取路径（驱动 + on-die ECC 芯片）对 spare 的可见性限制。

### 4.4 内核读路径分析（为什么两种模式都可能给 FF）

（源码存于 `/home/qc233/zte/e2631-p2/refs/`：mtdchar.c、spinand-core.c、mtdcore.c、foresee.c、mtd-abi.h。）
- `mtdchar_readoob` 按 fd 模式选择 `ops.mode = RAW ? MTD_OPS_RAW : MTD_OPS_PLACE_OOB`；
- `spinand_ondie_ecc_prepare_io_req` 先把 `spinand->oobbuf` 整体 memset 成 0xFF，再按 `req->mode != MTD_OPS_RAW` 开关 ECC；
- `spinand_read_from_cache_op` 读 OOB 时把 column 设为 page_size(2048)，用 dirmap 读 nbytes 到 `oobbuf`：
  AUTO_OOB 走 `mtd_ooblayout_get_databytes`，否则原样 memcpy；`spinand_mtd_regular_page_read` 在 RAW 时 disable_ecc；
- 两条路径都按设计执行，但返回的 spare 都是 FF——说明限制在芯片/控制器层面（见 §5），不是用户态参数错误。

## 5. ECC 布局结论（未证实）

### 5.1 主线静态证据（mainline foresee.c）

- `SPINAND_MFR_FORESEE = 0xCD`；F35SQA001G 的 READID 表项为 `0x71, 0x71`，
  `NAND_MEMORG(1,2048,64,64,1024,20,1,1,1)`：1024 块 × 128 KiB = 128 MiB，与系统报告完全一致；
- `NAND_ECCREQ(1,512)`（按 512 B 1-bit），与 sysfs 的 ecc_step_size=512 / strength=1 对应；
- OOB 布局函数对 ecc 区返回 **-ERANGE（无 ECC 区）**，free 区 offset=2、length=62（预留 2 B 给 BBM）；
- 即主线把字节 2..63 当“用户空闲 OOB”，**不向用户态暴露 ECC 校验位**；oobavail=62 与之一致。

### 5.2 对 research §4.4 假设的修正

research §4.4 的“每 16 B 段 8..15 为 ECC、0..1 为 BBM”来自 **heyangtek/GD5F 兼容布局**：
树 fork 的 patch 028 改的是 `drivers/mtd/nand/spi/heyangtek.c`（HYF1GQ4UDACAE），backport 436 也是 heyangtek。
本机 dmesg 明确是 **FORESEE**，因此该布局假设不适用于本芯片，应改用 foresee 布局判断（ecc=none、free 2..63）。

### 5.3 全 FF 的候选成因（本轮无法区分）

1. on-die ECC 的校验位不通过 64 B 用户 OOB 暴露（与 foresee 布局 ecc=none 一致）；
2. 芯片在 read-from-cache 读 spare 时统一返回 FF（ECC-on 与 ECC-off 都一样）；
3. 驱动/控制器的 OOB 读 op 变体问题——但主数据读取正常、RAW 模式也同 FF，可能性较低，需原厂内核/驱动对照才能排除。

要区分 1/2，必须换一条能真正读到物理 spare 的通道（见 §7 后续）。

### 5.4 对 P2 写回决策的影响

- ECC 布局未确认 → **编程器 ECC-on 回写可行性仍未验证**，不能把编程器当回滚路径；
- v2 编程器 dump 的 OOB 全 FF 不能解读为“OOB 为空”：可能同样是只导出主区或读模式掩蔽；
- 首选写通道仍是 C1（原厂 U-Boot 的 `nand write.uboot`，4-bit ECC）；首次写 boot 区仍按不可逆风险对待。

## 6. READID

- 内核日志只打印 “spi-nand spi0.0: FORESEE SPI NAND was found.” 与 128 MiB/128 KiB/2048/64 容量信息，**不打印原始 ID**；
- 由驱动匹配反推：厂商 ID 0xCD（SPINAND_MFR_FORESEE）；器件 ID 0x71 0x71（F35SQA001G，1024 块 = 128 MiB）；
  F35SQA002G 为 0x72/0x72（2048 块 = 256 MiB，容量不符），F35SQB002G 为 0x52/0x52（OOB 128，不符）——均排除；
- 厂商日志（research 引用）`manuid=cd chipid=71` 与之一致；
- 0xC9 假设排除：0xC9 属 heyangtek HYF1GQ4UDACAE（backport 436），与 dmesg 的 FORESEE 不符；
- 限制：本次没有用户态 SPI READID 通道（无 spidev、无 debugfs、无原厂工具），**原始 READID 字节未读取**；
  建议在 P1 用原厂 U-Boot 控制台的 nand info/READID 复核。

**结论：** READID = 0xCD 0x71 0x71，高置信推断，未经原始字节验证。

## 7. 结论与后续

已完成：mtd0-before 基线（de4ea5bd…）、U-Boot 区界 0x20000..0xC0000 核对（含 0x88840 实际内容边界）、
512 页 OOB 表与两种模式对照、跨分区对照、主线驱动布局分析、READID 推断。

**未完成/受限：** 真实 spare/ECC 位未观测 → ECC 布局未证实；编程器 ECC-on 回写未验证；原始 READID 未读。

后续建议（按优先级）：
1. P1 剩余项：原厂 U-Boot 控制台 `nand read`/`mtddebug` 语义基线（含 OOB 读命令），需要串口交互与用户配合；
2. 若编程器手册支持“ECC-off spare 读取”，按手册读一次并保留原始 bin；
3. 如需 Linux 侧再取证，可考虑 nanddump/nandwrite（需 Lead 批准安装或下载 apk 解包到 /tmp），
   但预期仍受 on-die ECC 可见性限制；
4. 对照原厂内核的 zx-spi/spinand 驱动，确认是否另有 OOB 读路径；
5. A3 移植任务核对 payload trailer（0x88800..0x88840）格式，避免重打包破坏尾部结构。

## 附录 C 工具源码要点

源码随证据入仓：`evidence/p2-oob/e2631-oobread.go`（与宿主 `/home/qc233/zte/e2631-p2/oobread/main.go` 一致）。
- `O_RDONLY` 打开目标 mtd 设备（优先 `mtdNro`）；
- 每页 `start = page * 2048`，`MEMREADOOB64` 读 64 B；
- `raw` 参数时先 `MTDFILEMODE = _IO(M,19) = 0x4D13`，模式 3（RAW）；
- 输出 = 512 × 64 B 顺序拼接；失败即非零退出并打印 errno。
