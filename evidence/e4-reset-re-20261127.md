## 1. 结论

1. 厂商 U-Boot 2013.04 的 reset 命令最终只做一件事：把 1 写进 TOPCRM 块的
   0x94000044 寄存器。处理函数先打印 "resetting ..."，等 50 ms，调用
   0x47f00840（mov r3,#0x94000000; mov r2,#1; str r2,[r3,#0x44]），然后返回；
   如果复位没有发生，它会回到命令行。
2. 这条路径里没有看门狗、没有 PLL/CRU 解锁、没有 cache clean/invalidate、
   没有 DDR/串口重配置、也没有写 flash。0x47f006ac（PLL 写解锁）、0x47f00534
   （cleanup_before_linux）、0x47f007c8/0x47f01338（PLL 设置）都不在 reset
   调用链上。
3. 0x94000044 的写入是整芯片复位：BootROM 重新打印 "Boot SPI NAND /
   start read bootheader / start read secondboot / non secure boot / Jump"，
   然后 secondboot 重新做 CRPM 与 DDR 初始化（"ddr init enter, rate is 1333
   Mbps"），再从 SPI-NAND 装载 U-Boot。两个不同时间的厂商串口会话都记录了同一
   顺序（§4）。因此复位前不需要保存 DDR/时钟/串口状态。
4. 我们的 U-Boot 里 do_reset() 已经打印 "resetting ..."、flush 控制台并关中断
   （arch/arm/lib/reset.c:33-44），所以补丁只需要实现 reset_cpu()：延时 50 ms、
   写 0x94000044=1、若复位未发生则自旋（不返回一个半死的命令行）。
5. 补丁草案：evidence/e4-reset-patch-draft-20261127.patch，1 个文件 +25/-4，
   基于 uboot-src HEAD cc2ec2ac（已含 0026）生成；git apply --check 通过，
   checkpatch --no-tree 为 0 errors / 0 warnings。没有新增任何 MTD 写路径，
   写白名单仍是 4 个站点，不碰 env、不碰 flash。
6. 需要一次零写入的设备验证（§8）：RAM 链装入带补丁的 U-Boot，在命令行执行
   reset，确认串口出现 "resetting ..."→BootROM→secondboot→新 U-Boot，且 mtd0
   sha256 不变。它不需要 A-series 授权门槛（没有看门狗/PLL 操作），但仍是真机
   行为证据，不能只靠静态逆向就宣布完成。

## 2. 输入与方法

- 厂商 U-Boot payload：evidence/p2-oob/vendor-uboot-ram.bin，426,048 B
  （0x68040），sha256 a4c640ad…；运行时链接地址 0x47F00000。
  地址换算：vaddr = 0x47F00000 + file_offset。
- 方法：capstone 5（CS_ARCH_ARM/CS_MODE_ARM，skipdata）对整个 payload 做线性
  反汇编（106,512 条指令），再用三类独立扫描交叉验证：
  1) 命令表项解析（6 个 32 位字：name/maxargs/repeatable/cmd_fn/usage/help）；
  2) BL/BLX 交叉引用扫描（找谁调用 0x47f00840）；
  3) "mov r3,#0x94000000 + str [r3,#0x44]" 数据流扫描与原始 32 位字面量扫描
     （找所有 0x94000044 写入）。
- 三个扫描结论一致：reset 处理函数唯一，0x47f00840 只有一个调用者，
  0x94000044 只有这一处写入。

## 3. 命令表项与处理函数

命令表项 0x47f5f1d4（file 0x5f1d4）的 6 个字：

    name      = 0x47f366db  "reset"
    maxargs   = 1
    repeatable= 0
    cmd_fn    = 0x47f01a40
    usage     = 0x47f36dab  "Perform RESET of the CPU"
    help      = NULL

reset 处理函数 0x47f01a40（file 0x1a40）：

    47f01a40: push    {r3, lr}
    47f01a44: ldr     r0, [pc, #0x1c]      ; literal @47f01a68 = 47f36b4a
    47f01a48: bl      #0x47f09adc           ; puts()
    47f01a4c: movw    r0, #0xc350            ; 50,000 us
    47f01a50: bl      #0x47f25688           ; udelay()
    47f01a54: bl      #0x47f0180c           ; stub: mov r0,#0; bx lr
    47f01a58: mov     r0, #0
    47f01a5c: bl      #0x47f00840           ; 写 0x94000044 = 1
    47f01a60: mov     r0, #0
    47f01a64: pop     {r3, pc}               ; 若复位未发生则返回

字面量与字符串：

    0x47f01a68 (file 0x1a68) -> 0x47f36b4a
    0x47f36b4a (file 0x36b4a) = "resetting ...\n"

被调用的复位叶子函数 0x47f00840（file 0x840）：

    47f00840: mov     r3, #0x94000000
    47f00844: mov     r2, #1
    47f00848: str     r2, [r3, #0x44]
    47f0084c: bx      lr

辅助函数确认：

- 0x47f09adc 是控制台输出包装（通过 gd->console 的 puts 回调）。
- 0x47f25688 是 udelay 的分块循环；0x47f01a4c 的 0xc350 = 50,000，即 50 ms。
- 0x47f0180c 是空函数（mov r0,#0; bx lr），没有硬件动作。

唯一性证据：

- BL/BLX 扫描：调用 0x47f00840 的只有 0x47f01a5c 一处。
- "mov r3,#0x94000000; str ...,[r3,#0x44]" 扫描：只有 0x47f00848 一处。
- payload 中没有 0x94000044 的原始字面量；没有其它写 0x94000044 的路径。
- reset 调用链中没有 0x47f00534（cleanup_before_linux）、0x47f006ac（PLL 写
  解锁）、0x47f007c8/0x47f01338（PLL 设置）、0x47f00560（看门狗命令）。

## 4. 复位效果的实测证据（厂商 U-Boot）

证据 A：evidence/c1b1a-write-rehearsal/run-2/serial-vendor-console-excerpt.txt，
第 39-61 行：

    39  => reset
    40  resetting ...
    42  Boot SPI NAND
    43  start read bootheader
    44  start read secondboot
    45  non secure boot
    46  Jump
    48  enter bootloader...
    49  crpm init enter
    50  crpm init done
    51  ddr init enter, rate is 1333 Mbps
    52  5ddr init done
    53  serial init start
    54  serial init done
    55  SPI NAND
    56  non secure uboot
    57  backup header!!
    58  Jump
    61  U-Boot 2013.04 (Aug 28 2023 - 18:40:22)

证据 B：evidence/b1-env-session/resume-serial.txt，第 70-92 行，顺序完全相同。

结论：

- "Boot SPI NAND / start read bootheader / start read secondboot" 是 BootROM 的
  启动流程，只有整芯片复位后才会重新出现；U-Boot 内部的 go 或单个外设复位不会
  打印这一段。
- secondboot 重新执行 "crpm init" 与 "ddr init enter, rate is 1333 Mbps"，
  说明 DDR 控制器和时钟被重新初始化；复位前不需要保留这些状态。
- U-Boot 自身与 env 都在 SPI-NAND（mtd0）里，复位后从 flash 重新装载；在 RAM 链
  中执行 reset 会回到 flash 里的 U-Boot，而不是 RAM 里的测试镜像（§7 R3）。
- 上述两次都是厂商 U-Boot 写 0x94000044；我们的实现写同一寄存器，仍需按 §8
  真机验证一次，不能把厂商行为直接当成我们代码的行为证据。

## 5. 我们 U-Boot 的调用路径

arch/arm/lib/reset.c（U-Boot 2027.01-rc2）：

    int do_reset(...)
    {
        puts("resetting ...\n");
        flush();
        disable_interrupts();
        reset_misc();
        reset_cpu();
        return 0;   /* NOTREACHED */
    }

因此：

- "resetting ..." 已由 do_reset 打印并 flush；补丁的 reset_cpu() 不再重复打印。
- 中断已关闭；我们的 U-Boot I/D cache 关闭（SYS_ICACHE_OFF/SYS_DCACHE_OFF），
  即使将来打开 cache，整芯片复位也会清掉，不需要额外维护。
- 50 ms 延时保留厂商顺序，作用是把最后一行控制台输出送出 UART 再复位。
- CONFIG_CMD_RESET 默认开启（help 里可见 reset）；不依赖 CONFIG_SYSRESET，
  也没有 sysreset 驱动参与，所以 do_reset 一定会调用 reset_cpu()。
- patch 0003 目前在 board/zte/zxhn-e2631/zxhn-e2631.c 末尾放占位 reset_cpu()
  （只打印 "A1 has no reset controller" 并返回），本补丁替换它。

## 6. 补丁草案

文件：evidence/e4-reset-patch-draft-20261127.patch（76 行，1 个文件 +25/-4，

基线：uboot-src HEAD cc2ec2ac "board: zte: add the web bootloader rescue
(e2631rescue)"，即已经包含 0026 的树；git apply --check 通过。因此补丁可以直接
排在 0026 之后；编号与系列中的位置待 base-builder 决定。

质量检查：

    git apply --check /tmp/e4-reset-draft.patch          # OK
    ./scripts/checkpatch.pl --no-tree /tmp/e4-reset-draft.patch
    # 最终：0 errors, 0 warnings, 0 checks, 43 lines checked

核心代码（补丁内最终形态）：

    #include <linux/delay.h>
    #include <asm/io.h>

    #define ZX279128S_TOPCRM_BASE       0x94000000
    #define ZX279128S_TOPCRM_SOFT_RST   0x0044

    void reset_cpu(void)
    {
        /* do_reset() has already printed "resetting ..." and flushed. */
        mdelay(50);
        writel(1, ZX279128S_TOPCRM_BASE + ZX279128S_TOPCRM_SOFT_RST);

        /* The vendor never returns here; do not resume a half-dead prompt. */
        while (1)
            ;
    }

补丁只改 board/zte/zxhn-e2631/zxhn-e2631.c：新增两个宏、两个 include，替换
占位 reset_cpu()。没有新增命令、没有新增 MTD 写路径、没有改 env。

## 7. 风险与限制

R1 寄存器语义没有公开文档：0x94000000 是 TOPCRM 块，内核 reset 驱动只描述了
   0x4c 的 USB 复位位（files/drivers/clk/zte/clk-zx279128s.c:41-52）；0x94000044
   在 A5/A6 会话的只读寄存器表里读为 0，厂商写 1 后整芯片复位。我们按同一 SoC
   同一寄存器实现，但"写 1 = 全局软复位"来自厂商行为而不是数据手册。若硬件修订
   不同，可能"写后不复位"（补丁自旋，需断电，不会变砖）或复位范围不同（需真机
   确认），所以 §8 的零写入验证是合并前的必要条件。
R2 复位不能发生在 e2631flash 的擦除/写入过程中。reset 命令只在 U-Boot 命令行
   使用；页面/救援流程仍然不自动重启。补丁验证通过后，页面成功提示可以从
   "断电重启"改成"可执行 reset"；验证之前继续写"断电重启"。
R3 从 RAM 链执行 reset 会回到 flash 里的 U-Boot（当前 mtd0 的镜像），不是 RAM
   里的测试镜像；这是 SPI-NAND 启动链的预期。只有 Phase 2 把新镜像真正写进 mtd0
   后，reset 才会进入新镜像。
R4 若 0x94000044 写被忽略，reset_cpu() 自旋，不返回状态被破坏的命令行；代价是
   人工断电，与现状相同，不新增变砖风险（写寄存器本身不写 flash）。
R5 厂商写之前等 50 ms；补丁保留该顺序，避免最后一行日志被复位截断。
R6 无看门狗、无 PLL/CRU 解锁、无 DDR 重配置，因此不触发 Lead 定的 A-series 门槛
   （"如果厂商路径需要踢狗 + PLL/CRU 写才需要 A-series"）。但真机验证仍要做。

## 8. 验证建议（下一次设备会话，零写入）

目标：证明带补丁的 U-Boot 执行 reset 后真的重启，并且没有写 mtd0。

1. 由 base-builder 在 0026 之后 git am 本补丁，产出新 U-Boot 构建；记录
   u-boot.bin sha256 与 banner（U-Boot 2027.01-rc2-g…）。
2. 按 task-75 §5 的 Phase 1 路径把该 u-boot.bin 装到 RAM（userdata 暂存 +
   mtd read 0x47F00000 + go；或串口 xmodem），不要写 mtd0。
3. 在 RAM 链的新 U-Boot 命令行执行 reset。
4. 期望串口顺序：
   "resetting ..." → "Boot SPI NAND" → "start read bootheader" →
   "start read secondboot" → "crpm init" → "ddr init enter, rate is 1333 Mbps" →
   "serial init" → "SPI NAND" → flash 里的 U-Boot banner。
   注意：RAM 链 reset 后进入的是 flash 的 U-Boot（当前 mtd0，不带本补丁），不是
   刚装入 RAM 的测试镜像；这是 R3 的预期，不算失败。
5. 复位前后各测一次 sha256sum /dev/mtd0（正常 Linux）或由串口 mtd read 回读
   比较；必须不变。
6. 若验证通过，把页面/文档里"reset 不可用，请断电"改成"可执行 reset"，由
   base-builder 合并后另行提交；本任务不改页面。

通过判据：一条 reset 命令完成重启（无需断电）；串口出现 BootROM 与 secondboot
的 DDR 初始化；mtd0 sha256 不变；U-Boot 命令行/救援流程没有新增 MTD 写。
