# F2 修复验证会话（2026-11-28，patch 0032 构建）

## 0. 结论摘要

- 本会话验证 patch 0032：把交换机转发控制寄存器 0x1cc000 从 BIT(17)=0x00020000 改为 17=0x00000011。内核驱动与厂商 bootloader 两处已知good路径都写 17。
- 会话 GREEN（2026-11-28 00:13:13–00:15:20，驱动 exit 0），探针结论 **F2_FIXED**：
  - 第一次 e2631net tx 3（pp 模式）就把 LAN1（端口 2）的 MAC TX frames 从 0 推到 3，主机 tcpdump 同时看到 3 个 60 字节广播 ARP，源 MAC 00:41:71:00:00:50。
  - 后续 pp-alt -> 6、vendor -> 9、pp+allow -> 12；整个会话 12 个 60 字节广播 ARP、12 个设备帧，全部来自 U-Boot MAC，第一次发送前为 0。
  - e2631net bmu 在端口未 start 时读到 switch fwd ctrl 0x00000000（该寄存器在 eth start 时编程），最终 bmu 读到 0x00000011（expected 0x00000011）；最终 e2631net 也打印 SW fwd 0x00000011。
- 一个独立的描述符变体观察：vendor-alt 段（queue 0 + word3 bit0=1）发送计数从 9 累计到 12，但 MAC TX frames 停在 9，网线 0 帧；随后 pp+allow 段又恢复增长到 12。默认 pp 模式（产品路径）不受影响，vendor 模式（word3 bit0=0）也能发送；vendor-alt 是单独待查项。
- 零写入：整场只有 Linux 侧 userdata staging（erase+write+readback+sync）；U-Boot 40 条命令无 mtd write/erase/saveenv/e2631flash，forbidden 列表为空。mtd0 前后均为 f923904049dd6bc5ed2a8b2598e2cbdf992ab2d7d5dc8c388ab2569237f659f4，镜像区前后均为 b1ea9a48f4b9c95f8764fcb0ffc5b088cd25c7064d27cb78321ffd3344bdf63a。
- env 块：B1 基线不变（stored CRC 0xf95a816e，region CRC 0xe826c394，块 sha 6e2c01da…）；env sanity 27 项，无 bad CRC/default env，ethaddr=00:41:71:00:00:50。
- F1：e2631boot -> KERNEL_STARTED，dt 8.68 s，Linux marker “Please press Enter”。postcheck 在 uptime 61 s 时 MT7916=0（WiFi 初始化尚未完成），随后只读复测 uptime 177 s：MT7916=1、WiFi complete=1。
- 无用户断电；设备最终回到 Linux，捕获链恢复（supervisor 328331 / bootwatch 328338 / tty 328337）。

- 累计：MAC TX frames 端口 2 依次 3 / 6 / 9 / 9 / 12；会话总计 15 次发送、0 失败（驱动计数）。
- vendor-alt 段是唯一没有增量的一段：驱动仍累计 sent 12，但 MAC TX frames 停在 9，窗口内 0 ARP、0 设备帧；下一段 pp+allow 又正常发送 3 帧到 12。vendor-alt 的描述符是 queue 0 + word3 bit0=1；vendor（word3 bit0=0）正常。默认 pp（产品路径）不受影响，这是描述符变体的独立观察项。
- 每个模式后 md.l 0x92340100 的 TM status 都会读清；最终 e2631net 打印 TM status 0x00000002、RX queue counts 17（收到的回包/广播计数）。
- SBRG 在发送前后保持一致：learn 0x00000000、port ctrl 0x000200ff、egress 0:0xfe 1:0xfd 2:0xfb 3:0xf7 4:0xef；sbrg allow 只是重放复位掩码。

## 5. 网线证据

- 全会话 34 帧；其中 12 帧源 MAC 为 00:41:71:00:00:50（U-Boot MAC），12 帧是 60 字节广播 ARP，12 帧为非主机帧；随机 MAC（26:a1:2f 前缀）0 帧。
- 第一次发送前窗口 0 帧；pp 段立刻出现 3 个 60 字节广播 ARP（tcpdump 原文：00:41:71:00:00:50 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 60: Request who-has 0.0.0.0 tell 0.0.0.0, length 46）。
- 主机自身 mDNS/IGMP/ARP 仍在各窗口出现，但归属已按源 MAC 区分。

## 8. 与 F2 历史会话的关系

- 前一探针会话（patch 0031，banner ge84e13107885）结论是 F2_PROBE_NO_MOVE：四种描述符变体全部无 MAC TX、无网线帧；当时 C2（egress mask）被排除，C3（VLAN1 全 0）保留，hw tx idx 不动。
- patch 0032 改的是转发控制寄存器 17；本会话第一次 tx 就产生 MAC TX 与网线帧，说明 F2 的根因就是该常量，不是 VLAN1/egress/描述符。VLAN1 仍全 0 但不再阻塞默认 pp 发送。
- vendor-alt 段不发送属于新的独立观察（描述符变体），不改变 F2_FIXED 结论。
