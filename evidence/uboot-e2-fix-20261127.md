# U-Boot E2 修复（task-69 items 1/2）：诚实 TX 错误 + BMU pending-retry + geometry 断言

- 日期：2026-11-27
- 任务：task-69 item 1（F2-a）与 item 2（防御性 geometry）；item 3（F1 bootm 内核交接）等 verify-docs 判别结果，item 4 已完成（`be1e405`/`b58bef9`）。
- 结论：patch 0023 修掉“`eth_send` 静默失败 + 超时 BMU 请求被丢弃”两个缺陷（移植内核 pending-retry）；patch 0024 把 staging / kernel copy / DMA arena 的几何写成编译期断言，并纠正卡片时代 `0x4554xxxx` 的换算错误。24 个 patch、post-am tree `721bb82538df42dca98fd633b98faa0582256850`，uboot-build CI 绿。

## 1. 背景与根因

task-68 的失败分析（[e2-session-failure-analysis-20261122.md](e2-session-failure-analysis-20261122.md)）给出：

- **F2-a（本次修复）**：`drivers/net/zx279128s_eth.c` 的 send 路径在 BMU 分配失败时直接
  `return -ENOSPC`，没有任何打印；U-Boot 的 `eth_send()` 只会 `debug()`（编掉），网络栈也不打印，
  所以串口只有 BOOTP 行、主机看不到帧。BMU 分配超时后请求仍留在硬件里，但驱动把它当成一次性失败，
  下一次 send 又写一次 REQ，**迟到的 buffer 永久丢失**。内核驱动对应位置有 pending 语义
  （`target/linux/zx279128/files/drivers/net/ethernet/zte/zx279128s-main.c:43-83`：
  `bmu_alloc_pending` + 下一次调用先收迟到 buffer），U-Boot 移植时漏掉了。
- **arena/staging 重叠假设被推翻**：3,491,146 B = `0x35454A`，从 staging `0x42000000` 起止于
  `0x4235454A`，与 arena `0x45000000` 相距 46.8 MiB；卡片里的 `0x4554xxxx` 是十进制/十六进制换算错误。
  因此 item 2 只做防御性断言，不移动 staging 或 arena。

### 2.1 patch 0023（F2-a）

- 移植内核 `zx_bmu_alloc_bp()` 的 pending 语义：`struct zx279128s_eth_priv` 增加
  `bmu_alloc_pending`/`bmu_alloc_fail`/`bmu_alloc_late`；分配超时后保持 pending，下一次 send 先
  poll 旧请求完成并收取迟到 buffer（计 `late`），不再新起请求把旧 buffer 丢掉。
- 与内核的有意差异：内核在 pending 仍挂起时立刻返回 `-EBUSY`（它的网络栈会重试）；U-Boot 是同步发送、
  调用方失败即丢帧，所以在 pending 路径上等同一个 `ZX_BMU_TIMEOUT_US`（1000 µs）再报错，
  只在这段等待后仍无 buffer 时才丢帧。
- 失败不再静默：send 打印
  `zx279128s: TX buffer allocation failed: <原因> (1 buffer required, <N>-byte frame; <fail> failed, <late> late; BUF_ALLOC=… BUF_ID=… FREE_STATUS=…)`；
  `e2631net` 增加 `BMU alloc <fail> failed, <late> late, pending <0/1>; BUF_ALLOC …, BUF_ID …` 一行。
  原因串覆盖 `-ETIMEDOUT` 与 `-ENOSPC` 两种。
- BMU 协议寄存器的写序列与 send 的 TX 描述符/门铃写序列**未改**；只增加读状态、等待与计数。

### 2.2 patch 0024（geometry，防御性）

- `drivers/net/zx279128s_eth.c`：arena 必须高于 `CONFIG_SYS_LOAD_ADDR`（staging）且 arena 末尾 ≤ `0x50000000`。
- `board/zte/zxhn-e2631/e2631flash.c`：bounce buffer（`0x44000000`）高于 staging；arena 高于 staging；
  staging 到 arena 至少留 48 MiB（`0x45000000-0x42000000`）；arena 末尾低于 relocated U-Boot 上限。
- `board/zte/zxhn-e2631/e2631boot.c`：kernel copy 窗口（`0x40008000 + 0x400000-0x20`）必须止于 staging 之下。
- README §3 新增“内存图”小节（见 [uboot-port/README.md](../uboot-port/README.md)）：staging 实测 3,491,146 B
  止于 `0x4235454A`，并明确 `0x4554xxxx` 是换算错误。

## 5. 真机复测协议（零 flash 写）

1. 用本产物进 RAM 链（或已装镜像的 flash 控制台），确认 banner `gcbcaeea0d172`。
2. `mii info`：四个 PHY 10-13 应出现；`e2631net`：记录 `BMU alloc … failed/late/pending` 与 `BUF_ALLOC/BUF_ID` 初值。
3. `dhcp`；失败时立刻再 `e2631net` 并记录计数与 BMU 三寄存器（`0x92348014`/`0x9234800c`/`0x923480dc`）。
4. 判读：出现 `TX buffer allocation failed` → 确实是 BMU 分配失败，按原因（超时/无 valid id）继续；
  没有该行但主机收不到帧 → 报文已交给硬件，转查 TX 描述符/端口或抓包；
  `late` > 0 说明超时后迟到 buffer 被正确收取（修复生效的直接证据）。
5. 全程不写 flash：主机抓包 + U-Boot 只读命令，staging 只写 Linux 侧 userdata（若走 Linux）。

## 6. 风险与边界

- pending 路径多等最多 1 ms/帧：只在 BMU 真的卡住时发生，BOOTP 帧量小，可接受；不会无限阻塞。
- 每次失败都打印一行：BOOTP 重试次数有限，不会刷屏；若将来 autoboot rescue 大量重试需要改成一次性提示。
- 计数只在本次启动内累计，不做持久化；`late`/`failed` 的语义是“超时后收迟到 buffer”/“分配失败次数”。
- geometry 断言是编译期常量检查，不能约束操作手输入的 staging 长度；staging > 48 MiB 仍会撞 arena（README 已写明）。
- 未改 `e2631boot` 行为、未改 0014-0017 语义、MTD 写调用点仍是 4 个（CI 白名单门禁通过）。
