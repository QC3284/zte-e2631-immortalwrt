### 4.1 写/读判别（完整 32 位地址）

| 地址 | 操作 | 回读 | CRC32 0x40 B |
|---|---|---|---|
| 0x42000000（suspect） | md 16 字 -> mw 0x11223344 x16 -> md 16 字 | 16 字全部正确 | 0x997fa966 |
| 0x4C000000（control） | 同上 | 16 字全部正确 | 0x997fa966 |
| 0x4A000000（control） | 同上 | 16 字全部正确 | 0x997fa966 |

说明 0x42000000 的写入与读回完全正常，不存在映射/缓存导致的写后不可见。

### 4.2 mtd read 判别

mtd read spi-nand0 0x42000000 0x2300000 0x800（读 slot1 首页）后立即 md 0x42000000 8 /
md 0x42000020 8 / crc32 0x42000000 0x20 / iminfo 0x42000020：

- md 看到 slot 标记 33333333 cccccccc 88888888 dddddddd + ffffffff...；
- 标记 CRC32 = 0x5076ace3（与主机对 32 B 标记重算一致）；
- md 0x42000020 看到 uImage 头（magic 56190527、ARM ImmortalWrt Linux-6.18.60）；
- iminfo 找到镜像（header 数据只读了 0x800，data CRC 报错是预期的截断，不是可见性问题）。

bdinfo 前后各做一次，结论相同（relocaddr 0x4ffa8000、reloc_off 0x080a8000、
suspect_below_reloc true），classification NO_ANOMALY，reloc_dependent=false。

### 4.3 历史异常更正

e2b-session-20261127.md 第 5 节和更早的 0x48000000 报告里的探针命令是：

- md 0x420000 8 -> U-Boot 解释为 0x00420000；
- crc32 0x420020 0x40 -> 0x00420020；
- iminfo 0x420020 -> 0x00420020。

这些地址与 0x42000000/0x42000020 无关，因此「md 看到数据、crc32 看到 0、iminfo 找不到」
是**探针读错地址**，不是 DRAM 可见性异常。同样的写法存在于 e2t_session.py（408-412 行）和
本驱动 F1 段的旧版；本驱动已在会话后修正。结论：

- 0x42000000 / 0x48000000 可见性异常**关闭**，归类为 harness 命令错误；
- 不需要为此增加产品侧断言或绕行；
- e2b-session-20261127.md 第 5 节加一行更正注记（不改写历史正文）。

### 5.6 判读与给 task-78 的建议

F2 的形式：驱动已经把端口“启动”起来（MAC ctrl/环/端口使能/TX start 都非零），但 MAC 的发送
计数器完全不增长，且线上 0 帧。这与 patch-0023（BMU 分配失败后的重试）无关——BMU 的
failed/late/pending 计数都是 0，BUF_ALLOC 也没有请求。更可能的位置：

1. TX 描述符所有权/门铃：eth_send 之后描述符的 OWN 位、prod/cons 指针、doorbell 寄存器是否
   真的被写；如果描述符没有交给 DMA，MAC 不会发帧，TX frames 也不会增长。
2. PP/交换机端口映射：lan1 对应 switch port 2 的 egress 表/端口映射是否正确，trap/转发目标
   是否指向 GMAC 端口；端口使能寄存器全 1 不代表 egress 表正确。
3. MAC 使能序列：对照内核驱动 start 后的 MAC ctrl 写入与 U-Boot 的差异（本次看到
   0x00BB2000，tftp 前 0x00BB2003；内核在 adjust_link 后会写不同的位），确认 TXEN 相关位。
4. 如果描述符/门铃都正常，再查 clock/reset（本会话 refclk 已验，但 eth_start 的 reset 序可能
   有顺序问题）。

建议 task-78 从“发送路径是否真的把一帧交给 DMA”入手：dhcp 一次后立即读 TX 描述符状态与
TX ring 的 prod/cons，再读 TX frames；如果描述符未被消费，问题在门铃/描述符；若被消费但
计数器为 0，问题在 MAC/PP egress。不要把 patch-0023 当作 E4 的主要修复方向。

### 5.7 局限

- e2631net 的 “BMU alloc 0 failed” 等计数是驱动软件计数，不是 MAC 硬件计数；这里与硬件
  BUF_ALLOC/BUF_ID 一致，可信。
- NIC 寄存器地址来自内核驱动对照；个别符号名（TX frames/octets）是按内核 main.c 的语义命名。
- dnsmasq 日志缺失（容器 stdout），但抓包与 BMU/NIC 快照足以支撑 NO_WIRE_FRAMES。
