分析对象: /home/qc233/zte/e2631-flash-dump-20261115/mtd0-bootloader.bin (1,048,576 B,

## 1. 分区整体布局（逐 64KB 块统计 FF/00/other）

## 2. 镜像头格式（发现）

两个镜像用同一头格式, 共 64B: `[16B 0x00][4B "128s"][4B LE 长度][剩余 0x00]`。
- secondboot: 长度 0x8000 (32KB); U-Boot: 长度 0x68000 (416KB)。
- `128s` 即 ROM/引导链认的产品魔数 (secondboot 代码里多处 `ldrb rN,[r0,#0xa6]; cmp rN,#0x34`
  逐字符比对该串)。
- 64B 头不在长度字段内 (U-Boot 载荷从 0x20040 起, 长度 0x68000 到 0x88040 与
  擦除区起点吻合)。

## 3. 运行时 env (0xC0000)

内容完整可读 (CRC 校验未通过任何标准窗口, 见 §5 待解):
```
baudrate=115200
bootcmd=setenv bootargs console=$(console) root=/dev/mtdblock8 ro rootfstype=squashfs  mem=$(memsize) ;
bootdelay=3            bootfile=uboot.bin        bootloaderfile=bootloader.bin
console=ttyAMA0,115200n8   ethact=eth0           ethaddr=00:41:71:00:00:50
fullfile=upgrade.bin   gatewayip=192.168.1.1    hostname=unknown
ipaddr=192.168.1.1     linuzfile=vmlinuz.bin    loadaddr=0x42000000
memsize=256M           netmask=255.255.255.0    netretry=5
serverip=192.168.1.100 stderr=serial            stdin=serial
stdout=serial          versioninfo=U-Boot V1.0.0 2023082…
```
要点: ①TFTP 参数族齐全 (ipaddr/serverip/netmask/loadaddr/bootfile) — 与实测
`tftp 0x43000000 <img>`+`bootm` 一致, 救砖通道就是它; ②loadaddr=0x42000000
(与 boot 日志 memtop:42000000 entry:40008000 一致); ③bootcmd 是回退路径
(设 bootargs 后走 cspboot 的固件头引导, 正常开机由 cspboot 逻辑主导);
④ethaddr 只是默认值, 真 MAC 在 tag 分区 (mtd1, e0:b6:68:ac:f3:d8)。

## 4. 安全链事实

- secondboot 内嵌 `0001ZXIC..` + `BOOTROM` + `RSA2048` 引用 (0x80-0xAC), 即
  ROM→secondboot→U-Boot 的 RSA2048 验签路径**存在**;
- 但 U-Boot 横幅自报 `non secure boot / non secure uboot` ⇒ 本机此链**关闭**,
  与包体 hdr_ofs=0 (未签名) 的事实互证;
- 推论: 刷自定义 U-Boot 无密码学关卡, 但要自己保证 bootheader 格式 (64B 头) 正确
  —— ROM 认 `128s`+长度, secondboot 认后续结构。

## 5. 待解问题
- env 块前 4B (affcec3e) 与 zlib CRC32(env[4:..]) 任何窗口都不匹配 — 可能是 ZTE 自定义
  校验/或该块另有格式 (内容本身逐字节可读, 不影响使用);
- `backup header!!` 精确语义 (secondboot 打印, 备份头指向 0x20000 还是另有位置) 需
  反汇编 secondboot 才能定;
- 0x10000/0xD0000 两段 64KB 全 0x00 的含义 (被写零的历史区域? 厂家预留?)
- 0x88040-0xBFFFF 的 248KB 擦除区是「给 U-Boot 的预留空间」还是旧镜像被擦的痕迹。

## 6. 对自定义 U-Boot 的意义 (更新 docs/多功能U-Boot可行性-2026-11-14.md)

- 已知包装格式: 64B 头 (16×0 + `128s` + LE 长度) — 新 U-Boot 可以直接按此打包;
- 已知空间预算: U-Boot 镜像区 0x20000..0x87FFF = 416KB (现镜像正好占满);
- 已知 env 位置: 0xC0000 (128KB 区), 可读可写;
- secondboot 在 0x0..0x803F 独立存在 ⇒ 自定义方案可以「不动 secondboot, 只换
  U-Boot 镜像」, 引导链第一段 (ROM→secondboot) 保持原厂, 风险面减半。
