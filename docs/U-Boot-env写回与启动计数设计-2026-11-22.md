# 自定义 U-Boot 的 env 写回与启动计数设计（D-U2，2026-11-22）

> 状态：设计（**Lead 2026-11-22 评审通过**；不含代码改动）。补丁编号：**0016 = class-1 跨槽回退**（已批准，先实现）、
> **0017 = env 写通道 / `e2631env`**（设计已批准；真机写 env 并入下一次已批准的刷机会话）。启动计数（class-2）
> 为 phase 2 设计，未排期。证据见 [evidence/p2-env-writeback-design-20261122.md](../evidence/p2-env-writeback-design-20261122.md)。

## 0. 结论摘要（给评审的 10 行）

1. **写通道选型 W1（推荐）**：保留 `CONFIG_CMD_SAVEENV`/`CONFIG_CMD_ERASEENV` 关闭，**不提供通用 `saveenv`**；
   只把 `env/mtd.c` 的 `.save` 指针从 `ENV_SAVE_PTR(env_mtd_save)` 改成 `env_mtd_save`，再新增一个
   **白名单 + 厂商键快照**的板级命令 `e2631env`（save/check/diff）。写路径本身（擦 128 KiB → 写 0x20000）
   U-Boot 主线已实现，不需要重写。
2. **格式完全兼容**：目标块就是厂商 `env_t` —— `[u32 LE CRC32][0x1FFFC]`，CRC 覆盖 data-only，
   偏移 `0xC0000`、长度 `0x20000` 与厂商逐字节一致；`ENV_SIZE` 算出来正好 `0x1FFFC`（证据 §2）。
3. **绝不启用 redundant env**：`CONFIG_SYS_REDUNDAND_ENVIRONMENT` 会把头部变成 5 字节并改变主/备选择，
   厂商 U-Boot 2013.04 会解析失败 —— 直接破坏回滚梯。CI 必须静态禁止。
4. **掉电安全**：擦写窗口内掉电 → CRC 失效 → 两链都回退**默认 env**（我方默认 env 有 `bootcmd=e2631boot`；
   厂商正常启动由 `zteboot_do_settings` 重建 bootargs/bootcmd 并自动 `saveenv` 自愈），**不存在只写 env 就把机器变砖的路径**；
   代价只是丢用户自定义变量，可由控制台 `e2631env` 或厂商链自愈恢复（证据 §4、§5）。
5. **0xE0000..0xFFFFF 放得下第二份拷贝，但 phase 1 明确不用**：它不是 U-Boot redundant 槽位（那会破坏兼容），
   自定义镜像拷贝只增加第二个写窗口与代码面；主块坏掉已有“默认 env 双链可启动”兜底。该扇区保留给 phase 2 状态账本，
   本阶段保持全 0xFF。
6. **厂商兼容是硬门**：任何一次 `e2631env save` 之后，必须能用 `loadx` 把厂商 U-Boot 装回 RAM、`go` 后
   `printenv` 正常解析并跑通厂商启动链；我们的写策略必须在导出前把 `bootcmd`/`bootargs`/`memsize`/`versioninfo`
   恢复为“加载时的厂商值”，否则会把 RAM-only 覆盖（`bootcmd=e2631boot`）持久化，造成两链互相改写 env。
7. **class-1 回退补齐（patch 0016）**：cspboot 对“槽无效/CRC 不合格”会自动换槽（实测语义），
   而我们 `e2631boot` 目前明确“no automatic fallback”（patch 0006:205）。先补这个**无持久状态**的等价回退，
   属于生产加固的第一优先，且不引入任何新 flash 写。
8. **启动计数（class-2，内核起来后挂死）本阶段不实现**，只给完整设计（§6）。原因：可靠计数需要每次启动的
   “尝试中”持久写入 + 用户态“健康”回写；而当前 DTS 把 `bootloader` 分区标为 `read-only`（DTS:362-366），
   用户态 `fw_setenv` 写不了 mtd0（只是 mtd0 read-only 的限制；可写分区如 `userdata` 的用户态 `mtd` 读写实测正常，见证据 §13）；打开它等于把引导区暴露给用户态。现有 `e2631-trial` 已提供
   **opt-in 的 600 秒用户态回退**（写的是可写的 slot 头，不碰 mtd0），本阶段继续用它覆盖 class-2。
9. **CI 断言**：uboot-build 门禁新增“写通道只经 `e2631env`、通用 saveenv/eraseenv 仍关闭、redundant 禁止、
   env 偏移/尺寸不变、二进制含擦/写与命令串、payload 预算不变”；`check-workflows.mjs` 静态校验这些门禁本身；
   `make check` 新增离线 `test_env_write_policy.mjs` 校验格式/CRC/厂商串/坏块防护/负例。
10. **评审决定（2026-11-22）**：Q1 = 不单独开设备会话，env 写入的验收动作并入下一次已批准的刷机会话（用户一次批准）；
    Q2 = **永久**保留通用 `saveenv`/`eraseenv` 关闭； Q3/Q4 = 推迟到 phase 2（届时首选通道 a，暂不把 `e2631-trial` 改为 `H_NEW` 驱动）；
    Q5 = **是**，0xE0000..0xFFFFF 登记为保留扇区并保持 0xFF（加 CI 断言）； Q6/Q7 维持建议、待 Lead 确认。

## 1. 现状与输入

- 运行镜像：v3，`u-boot.bin` 450,936 B（上限 `0x9F800`=653,312 B，余量 202,376 B），patch 0001–0013，
  mtd0 镜像 sha256 `f6d179da…`；CI run `44935007253` 的 UBOOT-INFO 记录上述值。
- env：`ENV_IS_IN_MTD=y`，`ENV_MTD_DEV="spi-nand0"`，`ENV_OFFSET=0xc0000`，`ENV_SIZE=0x20000`，
  `# CONFIG_CMD_SAVEENV is not set`（patch 0007 的 defconfig 行 36/37/45/50）。启动日志
  `Loading Environment from MTD... OK`（patch 0009）证明读路径与位置名都正常。
- 物理块：mtd0 位于 `0x0..0x100000`；env 块 `0xC0000..0xDFFFF` 恰为一个 128 KiB 擦除块；
  `0xE0000..0xFFFFF` 是同分区内第二个 128 KiB 擦除块，实测全 0xFF（mtd0 dump 0xC0000 段非 FF、0xE0000 段 uniq=1）。
- 工具：`tools/e2631-env.mjs` + `tools/lib/mtd0.mjs`（`ENV_OFF=0xC0000`、`ENV_BLOCK_SIZE=0x20000`、
  `ENV_DATA_SIZE=0x1FFFC`，`tools/lib/mtd0.mjs:21-29`）；离线重建 baseline 22 条 CRC `0xAFFCEC3E`，
  26 条目标块 CRC `0x573ADD31`/sha256 `9f46ed98…`，与证据文件一致（本任务已重跑复验，见证据 §3）。
- 写通道实证：C1b-1a dress rehearsal 已用我们 U-Boot 的 `mtd erase`/`mtd write`/`mtd read`/`cmp`
  在 `0x7F00000` 未用块完成写-读-擦全流程；C1b-1 正式写入 mtd0 `0x20000..0xC0000` 也已成功回读比对。
  **env 区（0xC0000）本身尚未被我们的代码写过**；Session B 的那次写入来自厂商 U-Boot 的 `saveenv`。

## 2. 目标格式（与厂商逐字节一致）

```
偏移 0x00000  u32 LE  CRC32(data)           （IEEE 反射多项式，初值 0；U-Boot crc32() 同算法）
偏移 0x00004  data[0x1FFFC]                （一串 NUL 结尾的 key=value，剩余补 0x00）
总长 0x20000 = 128 KiB = 一个擦除块
```

- U-Boot 侧：`env_t = {u32 crc; u8 data[ENV_SIZE]}`，`ENV_HEADER_SIZE=4`，`ENV_SIZE=CONFIG_ENV_SIZE-4=0x1FFFC`
  （`include/env_internal.h` 的 `ENV_SIZE` 定义；`CONFIG_SYS_REDUNDAND_ENVIRONMENT` 关闭时头部才只有 4 字节）。
- 厂商侧：同一格式已由两件事实证 —— (a) 我们从 mtd0 0xC0000 解析出 22/26 条并复算 CRC（`0xAFFCEC3E`/`0xF95A816E`）；
  (b) 厂商自己的 `saveenv` 会话后回读仍是标准块，且打印 `Environment size: %d/%ld bytes`（131068 = 0x1FFFC），
  字符串位于厂商载荷 file `0x38ed8`（vaddr `0x47F38ED8`）。
- **顺序不敏感**：vendor 按 NUL 串顺序导入；U-Boot `env_save` 导出顺序是哈希表顺序，和工具生成的字母序块不同，
  所以 CRC/sha 不同是正常的（Session B 的 `0xF95A816E` vs 工具 26 条 `0x573ADD31` 就是例证）。
  **任何校验都必须“解析后逐键比较”，不能拿 CRC 常量当相等判据**；CI/工具要遵守这条。

## 3. 写路径设计（W1）

### 3.1 为什么不用通用 saveenv

如果直接 `CONFIG_CMD_SAVEENV=y`，控制台会出现 `saveenv`；它导出当前 RAM env，而我们的
`board_late_init()` 已把 `bootcmd` 覆盖成 `e2631boot`（patch 0006 尾部），`e2631boot` 启动前还会
`env_set("bootargs", E2631_BOOTARGS)`。一次“顺手 saveenv”就会把这两个 RAM-only 值持久化，
再进厂商链时 `zteboot_do_settings` 又改回来并 saveenv —— 两链互相洗 env，增加无谓擦写与误判。
W1 把写入口收敛到一个命令里，导出前恢复厂商键快照，从根上避免这个问题。

### 3.2 组成

1. ~~`env/mtd.c`：`.save = env_mtd_save,`（替换 `ENV_SAVE_PTR(env_mtd_save)`，当前在 `env/mtd.c:342`）。~~
   **实现时改为 W1'：不碰 `env/mtd.c`，`.save` 保持 NULL，由 `e2631env.c` 自带五步写（见 §12）。**
   `ENV_SAVE_PTR` 宏仍保留给其它驱动；我们不打开 `CONFIG_CMD_SAVEENV`，所以 **不会编译出 `saveenv` 命令**，
   但 `env_save()`（`env/env.c:260`）能在驱动上找到非空 `.save` 指针并真正写 flash。
2. 新增板级命令 `e2631env`（建议新文件 `board/zte/zxhn-e2631/e2631env.c`，Makefile 加一行）：
   - `e2631env diff`：只打印“当前 env 将导出成什么样”，含条目数、data 长度、CRC、将被拒绝的键；不写。
   - `e2631env check`：读回 0xC0000 块，解析、重算 CRC、逐键打印；不写。
   - `e2631env save`：依次做（任一步失败即中止且不擦写）：
     a) `mtd_block_isbad(CONFIG_ENV_OFFSET)` 预检，坏块直接拒绝（见 §5.3）；
     b) 校验白名单：只允许 `e2631_*`、`bootdelay` 这类“我们的键”被改变；发现其它键与厂商快照不同 → 列出并拒绝，
        除非控制台显式加 `--force`（默认不给 force，实现时不加这个开关更安全）；
     c) 把 `bootcmd`/`bootargs`/`memsize`/`versioninfo` 恢复成 **env 加载完成时的快照值**（见 §3.3）；
     d) env 导出 → 本地重算 CRC → 打印 diff（键、旧值、新值）→ 调用 `env_save()`；
     e) 打印 `Saving Environment to MTD... OK` 与块回读校验结果。
3. 不打开 `CONFIG_CMD_ERASEENV`：`eraseenv` 对生产无必要，且它擦的就是 env 块，增加误操作面。

### 3.3 厂商键快照（vendor-managed keys）

在 `board_late_init()` 里、覆盖 `bootcmd` 之前，把下列 4 个键“加载时的原值”存进静态缓冲（约 300 B 上限，
不需要 malloc）：`bootcmd`、`bootargs`、`memsize`、`versioninfo`。缺失也记录“缺失”。
`e2631env save` 导出前恢复它们；写完后把 RAM 里的 `bootcmd` 再覆盖回 `e2631boot`（否则 autoboot 行为改变）。
这样：
- 厂商链读到的这些键与我们写入前一致；`zteboot_do_settings` 比较后不会因我们而产生额外改写；
- 用户的 `e2631_*` 变量照常持久化；
- 其它厂商键（ethaddr/ipaddr/serverip/…）原样保留。

### 3.4 擦写算法与不变量

`e2631env save` 的实际擦写全部复用 U-Boot 主线 `env_mtd_save()`（`env/mtd.c:33`），顺序如下：

```
1. mtd_block_isbad(mtd, CONFIG_ENV_OFFSET)          -> 坏块则拒绝（不擦不写），打印原因
2. 读取当前块 0xC0000..0xDFFFF（0x20000），解析并算 CRC -> 生成 diff
3. 语义相等则直接返回 0（不擦写；见下方快速路径）
4. mtd_erase(ei.addr=0xC0000, ei.len=0x20000)       -> 只擦这一个 128 KiB 块
5. mtd_write(ei.addr=0xC0000, ei.len=0x20000)       -> 按 writesize（SPI-NAND 0x800）分块写
6. 回读 0x20000，解析、重算 CRC、逐键复核            -> 不符则报错（此时 env 已在 flash 中损坏）
```

关键点：

- **一个擦除单位**：`CONFIG_ENV_SIZE(0x20000) == erasesize(0x20000)`，`env_mtd_save` 走
  “整扇区”分支（`sect_num = DIV_ROUND_UP(0x20000, 0x20000) = 1`），擦除范围恰好
  `0xC0000..0xE0000`。**没有跨块、没有第二扇区**；这是与厂商布局完全相同的最小写入面。
- **坏块旁路是设计要堵的坑**：`env_mtd_load/save` 的读写循环遇到坏块会 `offset += sect_size` 后继续，
  对单扇区 env 而言，若 0xC0000 恰为坏块，该扇区会被**静默跳过**、写循环空转返回 0（跨多扇区的 env 才会挪到下一扇区），而厂商链固定读 0xC0000 —— 结果是我们以为写了、
  厂商读旧/空块。因此 W1 在 save 前显式 `mtd_block_isbad(0xC0000)`，坏块直接拒绝并提示人工处理，
  绝不静默搬运（见 §5.3）。
- **快速路径（幂等保存）**：`e2631env save` 先把“候选块”与“当前 flash 块”都解析成键值集合；
  若没有需要持久化的差异（例如只是 `bootcmd` 被 RAM 覆盖，恢复快照后与原块等价），直接打印
  “no change, env block left untouched” 并返回 0，不产生擦写。这条让“顺手多存一次”不消耗擦写寿命，
  也减少一个掉电窗口。
- **只写 env 块**：候选块长度恒为 0x20000；代码里对 `ENV_OFFSET`/`ENV_SIZE` 做编译期断言
  （`static_assert` 等价物：`BUILD_BUG_ON`），保证偏移 0xC0000、长度 0x20000 不随 config 漂移。
  擦除/写入地址只由这两个宏计算，不接受命令行动态地址参数 —— 没有“手滑擦 0x0”的接口。

### 3.5 0xE0000..0xFFFFF 是否可以放备份副本

**物理上可以，本阶段明确不用。**

- 事实：mtd0 是 1 MiB，0xC0000..0xDFFFF 是 env 块，0xE0000..0xFFFFF 是同分区内**第二个 128 KiB 擦除块**，
  实测全 0xFF，未被任何链读取；厂商 `saveenv` 的日志是 `Erasing 0xc0000 - 0xe0000`，也只擦 env 一块。
- 不能用 U-Boot 原生 redundant env：`CONFIG_SYS_REDUNDAND_ENVIRONMENT` 会 (a) 把头部扩成 5 字节、
  (b) 主备选择依赖 flags 字节，厂商 2013.04 的 env 导入逻辑只认 4 字节头 + 0x1FFFC 数据 —— 一旦启用，
  厂商链读到的就是错位块，直接破坏回滚梯。**CI 静态禁止**（§8.1）。
- 自定义镜像副本（自己加 magic + CRC 写到 0xE0000）技术上可行，但收益有限：
  - **厂商链根本不读 0xE0000**，所以它救不了“厂商链读到坏 env”的场景；能救的只是“我们的自定义变量丢失”；
  - 我们的链在 env 坏时本来就会回退到**编译期默认 env**（`CONFIG_BOOTCOMMAND="e2631boot"`），照样能启动；
  - 多一份拷贝 = 每次 save 多一次擦+写 = 多一个掉电窗口和更多代码分支，风险净增加而不是减少。
- 决策：phase 1 保持 0xFF；**Q5 = 是：登记为保留扇区**（2026-11-22 评审），phase 2 若要“启动状态账本”可放这里
  （厂商忽略该区域，天然隔离），但必须另开评审、加地址断言、并在 CI 中锁死。

## 4. 掉电安全与风险

### 4.1 掉电窗口表

| # | 掉电发生在 | flash 上 env 块状态 | 我们的链 | 厂商链 |
|---|---|---|---|---|
| W1 | 擦除开始前 | 旧 env 完整 | 正常 | 正常 |
| W2 | 擦除过程中 | 旧块部分变 0xFF/垃圾 | CRC 失败 → 默认 env → `e2631boot` 正常 | `zteboot_do_settings` 重建并 saveenv 自愈 |
| W3 | 擦完、写开始前 | 全 0xFF | CRC 失败 → 默认 env | 同上（env 空 → 默认 → 重建保存） |
| W4 | 写入过程中 | 头部 CRC + 部分数据 | 绝大多数情况 CRC 失败 → 默认 env；极小概率“恰好写完整”则新 env 生效 | 同上 |
| W5 | 写完、回读前 | 新 env 完整 | 正常（新值） | 正常（除非我们把厂商键改坏 —— W1 的快照机制防这个） |

要点：**env 块是“可丢”数据，不是引导代码**。任何窗口的最坏结果是丢自定义变量，两链都能用默认 env 启动到
`e2631boot` → slot 选择 → 内核；不存在“只写 env 就变砖”的路径（这是与写 secondboot/U-Boot 区段的本质区别）。

### 4.2 双链兜底的事实依据

- 我方：`env/common.c:443-456` `env_import()` 校验 CRC 失败时调用 `env_set_default("bad CRC")`
  （`env/common.c:388`），默认 env 来自编译期 `CONFIG_BOOTCOMMAND="e2631boot"` 与 defconfig 的
  `CONFIG_BOOTDELAY=3`；`board_late_init()` 无论 env 好坏都会再把 `bootcmd` 设为 `e2631boot`。
  所以 env 坏 → 启动路径不变。
- 厂商：正常启动在跑 bootcmd 之前先 `zteboot_do_settings 0x47f163bc`，从内置字符串重建
  `bootargs/bootcmd/memsize/versioninfo` 并在不同时 `saveenv`（证据笔记 §4 列了每条指令地址）。
  即厂商链对坏 env **有自愈写入**；我们不需要替它做备份。
- slot 选择不依赖 env：`e2631boot` 与 cspboot 都从 slot 版本头（magic+CRC1+serial）选槽，
  env 只影响 bootargs/菜单行为。

### 4.3 风险表（brick paths 与缓解）

| 风险 | 触发条件 | 影响 | 缓解 / 状态 |
|---|---|---|---|
| R1 擦错地址 | 代码 bug 把擦除地址算成 0x0 或 slot 区 | 引导区被擦 → 真砖 | 擦除地址只能来自 `CONFIG_ENV_OFFSET` + 编译期断言；命令无地址参数；CI 断言 + 测试用例（§8） |
| R2 坏块静默搬运 | 0xC0000 为坏块，`env_mtd_save` 顺移写 0xE0000 | 厂商读旧/空 env；我们读到旧值 | save 前 `mtd_block_isbad` 拒绝；回读校验地址；证据 §5.3 |
| R3 掉电 | 见 §4.1 W2–W4 | 丢自定义变量，两链默认 env 启动 | 已论证非砖；恢复用 `e2631env` 重设或厂商链自愈 |
| R4 两链互相洗 env | 通用 saveenv 把 RAM 覆盖持久化 | 反复擦写、误判 | W1 收敛写入口 + 厂商键快照 + 不提供通用 saveenv（§3.1/§3.3） |
| R5 写坏厂商键 | 用户 `setenv bootcmd …; e2631env save` | 厂商链行为被改 | 白名单只放行 `e2631_*`/`bootdelay`；厂商键导出前恢复快照；diff 打印并需显式 save |
| R6 用户态误写 mtd0 | 打开 DTS read-only + fw_setenv | 引导区暴露给用户态 | 本阶段不改 DTS；phase 2 若选通道 b 必须单独评审（§6.4） |
| R7 擦写寿命 | 每次启动都 save（计数设计） | P/E 消耗 | phase 1 不写；phase 2 上限估算 ~27 年（10 次/天，见 §6.4） |

**“不是零风险”的诚实说明**：上述论证依赖两个前提 —— (a) 我们的 SPI-NAND 驱动擦/写/回读在这些块上行为正确
（C1b-1a/1 已在别的扇区验证，env 扇区本身尚未实写）；(b) 擦写期间电源/复位行为符合预期。
因此 Q1 的验收动作（**写 env 块 + 回读 + 冷启动 + 厂商链复核**）不单独开会话，而是并入下一次已批准的刷机会话，
作为实现补丁合入前的验收动作；在该动作完成前，本设计不声称“已在真机验证”。

## 5. 坏块、擦除失败与恢复梯

### 5.1 预检（写前）

`e2631env save` 在任何擦除之前做：

1. `mtd_block_isbad(mtd, CONFIG_ENV_OFFSET)` —— 坏则拒绝，打印
   “env block 0xC0000 is marked bad; refusing to write (vendor chain reads this fixed offset)”；
2. 只读回读 0x20000 并解析：若块内是**全 0xFF**（从未写过）也允许 save（属于首次写入场景）；
   若解析失败/CRC 错，仍允许 save（这正是要修复的状态），但先打印“current block invalid: …”；
3. 编译期断言 `CONFIG_ENV_OFFSET % mtd->erasesize == 0` 且 `CONFIG_ENV_SIZE == mtd->erasesize`，
   运行时若 SPI-NAND 报告的 erasesize 不是 0x20000（驱动/设备树漂移）→ 拒绝写并打印实际值。

### 5.2 擦除/写入失败

- `mtd_erase` 返回非 0：打印 `errcode`，**不自动重试**（重复擦同一块只会扩大“部分擦除”状态，且掩盖 bug）；
  命令行返回失败，提示“cold boot and check e2631env check”。此时块可能处于部分擦除态，
  下次启动按 §4.1 W2 处理（默认 env，两链可启动）。
- `mtd_write` 返回非 0：打印已写偏移与 `errcode`；**不自动重写**（避免在电源不稳/坏块上前滚）。
- 回读不一致：判定 save 失败（即使 write 返回 0）——这是唯一可信的“写完”判据；
  打印首个不一致偏移、期望/实际 CRC，并注明“flash env 当前内容不可信，重启将以默认 env 启动”。

### 5.3 为什么必须拒绝坏块

U-Boot 的 MTD env 驱动为“大 env 跨多扇区”设计：读写循环里遇到坏块会 `offset += sect_size` 跳过。
对 `sect_num == 1` 的情形，这意味着 0xC0000 被**跳过**、写循环空转返回 0（跨多扇区时才会写到下一扇区），而：
- 厂商链（cspboot/do_settings/saveenv）**永远读 0xC0000**；
- 我们的 `env_mtd_load` 下次也会先读 0xC0000；
于是“写成功”是一句空话。预检拒绝 + 回读地址断言，是把这个静默失败变成显式失败。

### 5.4 恢复梯（env 相关）

```
正常：两链任意启动
  ↓ env 块坏（掉电/坏块/手滑）
默认 env：我们的链 bootcmd=e2631boot → slot → 内核；厂商链 do_settings 自愈并 saveenv
  ↓ 若用户想恢复自定义变量
控制台 e2631env（实现后）或 setenv + e2631env save；厂商链 setenv + saveenv 也可（格式相同）
  ↓ 若引导区本身被写坏（不属于 env 设计）
vendor U-Boot 经 loadx 装回 RAM → 修复；最后手段：编程器整片恢复（docs/救砖手册-2026-11-15.md §6.6/§6.7）
```

## 6. 启动计数与槽回退

### 6.1 cspboot 的实际语义（作为对标）

从厂商 RE 与抓到的启动日志，cspboot 的选择/回退是**两段式、无状态**的：

| 情形 | cspboot 行为 | 依据 |
|---|---|---|
| 两个槽版本头都合法 | 选 serial 较大者；相等取 slot0 | `pdt_getimgindex` 打印 `select = 1, serial0=0x7, serial1=0xc`；A3/slot 设计文档 |
| 选中槽的 kernel/rootfs CRC 不合格（class-1） | 判该槽无效，**自动改启另一个合法槽** | `pdt_getreal_kernelfs` 走 `csp_crc` 校验；日志 `not found vaild fs!! -> Total found 2 firmwares(valid:1), start from ver 0`（docs/02-实施计划-2026-10-13.md:360-363） |
| 内核已启动但挂死/起不来用户态（class-2） | **无自动补救**；没有尝试计数、没有“上次启动失败”状态 | `pdt_getimgindex` 只比较 serial；RE 未见任何计数/回写；同文档 :363-368 明确“class-2 无自动恢复” |
| env 坏 | 重建默认 env 并 saveenv | zteboot_do_settings（§4.2） |

结论：cspboot 的“回退”= **class-1 的即时 CRC 重选**，不是“连续失败 N 次后换槽”。后者的“N 次”必须靠持久状态，
而 cspboot 没有；它所谓“断电两三次会回去”只对 class-1 成立（每次启动重新校验 CRC 自然换槽）。

### 6.2 我们的 e2631boot 现状与差距

补丁 0006 的 `e2631_boot()`：按 cspboot 同样的规则选槽（magic+CRC1+serial），读 `slot+0x20` 的 legacy uImage，
校验 hcrc/类型/压缩、载入 0x42000000、校验 dcrc、设 bootargs、`bootm 0x42000020`。
差异（patch 0006 源码内已注明，:205）：“**There is no automatic fallback to the other slot.**”
任一校验失败 → 打印原因 → 返回 `CMD_RET_FAILURE`（:315/:336/:349），**不尝试另一个槽**。

因此：
- class-1（选中槽 uImage 坏、另一槽好）：cspboot 能起，我们不能 —— **这是生产加固必须补的 parity 缺口**；
- class-2（内核挂死）：两链都没有自动补救；我们现有 `e2631-trial`（opt-in，600 s）覆盖一部分。

### 6.3 phase 1：patch 0016（class-1 parity，无状态、无写 flash）

改动只在 `board/zte/zxhn-e2631/e2631boot.c`（约 +70/−10，单文件）：

1. 把“选槽”与“启动一个槽”拆成 `e2631_pick_slot()` / `e2631_try_boot_slot(slot)`；
2. `e2631_boot()`：先按规则试选中槽；**任何** uImage 级失败（header 读失败、magic/type/os/comp 不支持、
   hcrc 错、读数据失败、dcrc 错）→ 打印
   `e2631boot: slotX unusable (<reason>), falling back to slotY (cspboot class-1 parity)`，
   再试另一个槽；
3. 两槽都失败：打印两行原因后返回失败（行为与现在一致，不写任何 flash、不改 serial/H_NEW）；
4. **不做**：不改版本头/不升 serial/不写“上次启动失败”标志/不计数。选槽规则与 cspboot 保持一致，
   避免出现“我们选 A、厂商选 B”的分裂；
5. 静态可测点：日志串固定、无 `mtd_write`/`mtd_erase`/`fwslot` 调用、payload 预算不变（§8）。

这条是**纯收益**：不引入新持久状态，失败时只是多试一次；成功时行为与现在完全相同。

### 6.4 phase 2：启动计数设计（本阶段只设计，不实现）

目标：覆盖 class-2 —— 内核起了但用户态不健康，连续 N 次后自动一次性切到另一个槽。

**env 变量**（都在白名单内，随 `e2631env save` 持久化）：

| 变量 | 语义 | 默认 |
|---|---|---|
| `e2631_bootcount` | 当前“连续未确认启动”计数，0..max+1 饱和 | 无（视为 0） |
| `e2631_maxcount` | 阈值 N；0 = 关闭计数 | 3 |
| `e2631_count_slot` | 计数所属槽（0/1），槽变了就清零重记 | 无 |

**状态机**（每次 `e2631boot`）：

```
selected = cspboot 规则选出的槽（§6.1）
if e2631_maxcount == 0: 直接启动 selected（不读不写计数）
if e2631_count_slot != selected: count = 0; count_slot = selected; 需要一次 save
count += 1; save（失败只打印，绝不阻断启动）
if count > maxcount:
    另一个槽合法? 是 → 本次一次性启动它，count = 0, count_slot = 另一槽, save, 打印醒目告警
                      否 → 仍启动 selected，count 保持饱和，打印“no alternative slot”
启动 selected/另一槽
```

**“成功”由谁确认**：U-Boot 自己无法知道内核/用户态是否健康，必须有用户态健康信号。三个通道：

- **通道 a（推荐）**：复用 slot 版本头的 `H_NEW` 字节（偏移 slot+0x1500000+0x1f8，`e2631-fwslot.c:98`）。
  fwslot 刷写时已写 `H_NEW=1`（:1118），但**全树没有任何读取者**（grep 只有定义+写）。设计：
  U-Boot 启动前若 `H_NEW==0` 且 `bootcount>0` → 认为上次启动已被用户态确认，清零计数（一次 save）；
  用户态健康检查（e2631-trial/commit 或新脚本）确认后把 `H_NEW` 清 0（写的是**可写的 slot 头**，不碰 mtd0）。
  cspboot 不读 `H_NEW`/`H_CRC2`，所以不影响厂商选择；写 slot 头有掉电风险但只影响该槽“未确认”标志，
  最坏表现为多一次回退尝试，不破坏内核/rootfs。
- **通道 b（不推荐）**：打开 mtd0 `read-only`（DTS:362-366）让 `fw_setenv` 写 env。效果直接，但把引导区
  暴露给用户态，任何用户态 bug/误操作都可能碰 mtd0 —— 违背“env 写入口收敛”的初衷。现场已证明用户态
  `mtd` 工具对可写分区（如 `userdata`）读写正常（证据 §13），所以 b 的争议点不是“写不了”，而是“是否把 mtd0
  开放给用户态”。若将来必须用，需单独评审并加 `fw_env.config` 锁 + 只读备份流程。
- **通道 c（本阶段现状）**：不实现计数，继续用 `e2631-trial`（opt-in、600 s、用户态回退）。
  它已覆盖“新固件起不来用户态 → 回滚”，代价是需要手动布防（`/etc/e2631-trial-arm`）；
  默认布防曾造成“为什么自己回原厂”的困惑，所以保持默认关。

**代价与寿命**：开启计数后每次启动至少 1 次 env 擦写（count+1），回退/确认时再多 1 次；按每天 10 次启动 ≈ 3650 次/年，
SPI-NAND 100k P/E 下约 27 年 —— 寿命不是问题；真正成本是**每次启动多一个掉电窗口**和状态机复杂度。
因此 phase 2 必须：只在 `e2631_maxcount>0` 时写、写失败绝不阻断启动、每次写前 `mtd_block_isbad` 预检、
回读校验，并复用 phase 1 的 W1 写通道（不新开写路径）。

### 6.5 明确“不做什么”

1. **不在 phase 1 做任何“每次启动”的 flash 写**（计数、时间戳、尝试记录都不做）；
2. **不启用 U-Boot redundant env**（破坏厂商格式，§3.5）；
3. **不改 `ENV_OFFSET`/`ENV_SIZE`**，不新增 env 分区，不动 DTS 分区表；
4. **不自动使用 0xE0000 做 env 备份**（§3.5）；
5. **U-Boot 不改 slot 头的 serial / 不伪造 `H_NEW`**（唯一例外是 phase 2 通道 a 的“清 0 确认”，需单独实现评审）；
6. **不做永久换槽**：回退只对本次启动生效，下次仍按 serial 规则选（避免“回退后永远回不去”的暗状态）；
7. **不因计数写失败而阻断启动**：写失败 = 本 boot 少一次计数，不是启动失败；
8. **不把通用 `saveenv`/`eraseenv` 当日常入口**（W1）；
9. **不在本阶段移除 DTS `read-only`**（通道 b 的前提，需单独决策）；
10. **不在没有用户态健康信号时做 class-2 自动回退**（否则会在“内核正常但用户态慢”时误回退，制造假故障）。

## 12. 实现注记（2026-11-22，task-64 交付后补）

**W1 的 .save 直连在实现时被放弃**：0017 没有改 env/mtd.c，env_save 保持 NULL，saveenv/eraseenv 继续编译掉；
五步写（坏块预检 → 擦除 → 全 0xFF 校验 → 写入 → 回读逐字节比较）由 board/zte/zxhn-e2631/e2631env.c 自查
CONFIG_ENV_OFFSET/CONFIG_ENV_SIZE 完成，因此通用 env_mtd_save()（擦除后直接写、无全 FF 校验、单扇区坏块
静默跳过）根本不存在于镜像里。D-U1 的调用点白名单因此覆盖恰好两个安全 writer：e2631flash（两个 helper）与
e2631_env_write_block（两个调用点），共 4 个 MTD 写调用点；结构上比 W1 更收敛，代价是设计稿 §3.2/§7.1 的
“.save 一行”不再适用。

**另一处保守化**：当前 env 块非空但 CRC/解析坏时，e2631env save 拒绝重建（设计稿 §5.1 允许重建）。原因是
坏 CRC 时 U-Boot 回退到编译期默认 env，board_late_init() 的快照里没有 ethaddr 等厂商键，重建会静默丢键；
恢复通道改为让厂商链的 zteboot_do_settings 自愈（它会重建并 saveenv），或由用户在控制台显式修块后再 save。
空白块（全 0xFF）仍允许首次写入。
