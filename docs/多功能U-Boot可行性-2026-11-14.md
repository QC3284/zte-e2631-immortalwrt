# E2631 多功能 U-Boot 可行性分析（2026-11-14）

结论先行：**有条件可行，但不是现在该做的项目。** 三条支柱让它在原理上走得通
（无签名启动链 + 厂商控制台支持 tftp/bootm 的零风险试验路径 + U-Boot 2013.04 的 GPL
源码可索取），但成本集中在「把 SPI-NAND 与有线网络驱动移植进 U-Boot」和「引导区格式
逆向」两块，属周~月级工程。现有体系（A/B 槽 + fwslot + failsafe + 串口控制台 + TFTP
RAM 引导）已经覆盖了社区「多功能 U-Boot」的大部分恢复价值。本文件把证据、映射、风险
与分阶段建议落盘。

## 1. 本机引导链现状（全部 A 级实测或本仓库文档定案）

- 上电链：ROM `Boot SPI NAND` → 读 bootheader → 读 secondboot（日志里有 `backup header!!`
  字样，暗示引导区有冗余头机制，语义未验）→ **U-Boot 2013.04 (Sep 25 2024)**，
  `Board: ZTE zx279128sevb`，`DRAM 256 MiB`，`non secure boot / non secure uboot`
  （docs/01-情报汇总与事实核验-2026-10-13.md:113-115；串口抓取 S1 日志）。
- 引导区：mtd1 Bootloader 1MB 明文 + mtd2 tag 1MB 明文，本地已有完整备份
  mtd1-bootloader.bin sha256 66c15e9199fd91c7…38ff17bd4
  （docs/02-实施计划-2026-10-13.md:643）。**本仓库没有任何 U-Boot 源码**——整个项目
  至今零改动引导链（包体 bootIncl==0，docs/architecture.md:82）。
- 厂商控制台：上电按 `1` + 密码 `5cE080@fyBD` → `=>`；已实证 `tftp 0x43000000 <img>`
  + `bootm 0x43000000` 引导 **12.7 MiB uImage 成功**（mainline 6.18.38 进 busybox 壳，
  docs/01-情报汇总与事实核验-2026-10-13.md:116-117）。
- 选槽：cspboot 每 128 KiB 扫 flash 找内层魔数、只验 CRC1；serial 大者胜、相等起槽 A；
  **起不来不自动回退**（docs/01-情报汇总与事实核验-2026-10-13.md:87-91）。
- 同族先例（重要）：SR1010/ZX279133（cnjn 生态）**已经在生产环境改过厂商 U-Boot**——
  「打了 U-Boot 一条 bl malloc→固定地址」绕开 ~8MiB 堆拷贝上限
  （docs/H3600镜像体积与E2631原厂supgrade刷入可行性-2026-10-12.txt:157-158），且其
  sysupgrade 直接 --patch-uboot（docs/02-实施计划-2026-10-13.md:287）。差异：SR1010
  每槽自带 U-Boot 拷贝；E2631 包体不含引导（UBOOT_SIZE=0），U-Boot 只活在 mtd1。

## 2. 「多功能 U-Boot」逐项映射

社区语境的多功能 U-Boot（MT798x 系）通常指：Web 刷机恢复界面 + 开机选系统菜单 +
TFTP 恢复 + 免拆机救砖。逐项对照本机：

| 功能 | 现状 | 到「多功能」的成本 |
| --- | --- | --- |
| Web 恢复界面（浏览器上传固件） | 无 | **最高**：U-Boot 里需要 GEPHY×4 + zx279128s-mdio(0x9a101000) + TM/NPP 包引擎的网口驱动 + lwIP/HTTP 栈。上游 U-Boot 无任何 ZXIC 目标，全部要从厂商 SDK 移植；这些控制器连 mainline Linux 都是本移植项目才带上的 |
| 开机选槽菜单 | 半有 | **低**：厂商控制台已能进 U-Boot 壳；补一个 bootcmd/env 菜单即可，但 env 存在 flash，改 env 的格式要先逆向 |
| TFTP 恢复 | 已有 80% | 厂商 U-Boot 的 tftp+bootm 实测可用 → 救砖通道今天就存在，缺的只是「自动起 TFTP 服务端拉固件」 |
| 双系统切换 | 已有 | fwslot switch 四字节改 serial 即可（e2631-fwslot）；U-Boot 菜单只是把它挪到开机时刻 |
| 免拆机救砖 | 已有 | failsafe + 串口 + TFTP RAM 引导 + 槽 B 原厂兜底；唯一真砖场景=双槽全坏+引导区损坏 |
| 图形/网页化 | 无 | 纯工作量的花活，价值最低 |

即：**「多功能 U-Boot」真正稀缺的两项 = Web 恢复界面 + 开机菜单**，而它们依赖同一件
我们没有的东西——U-Boot 里的网口/SPI-NAND 驱动。

## 3. 三条可行性支柱

1. **无签名墙**：U-Boot 自报 `non secure boot`，包体头 hdr_ofs=0 即未签名
   （docs/01-情报汇总与事实核验-2026-10-13.md:32）；原厂的 RSA 只存在于**网页上传器
   的软件层**（docs/known-issues.md C 组）。意味着自研 U-Boot 不需要过任何密码学关。
2. **零风险试验路径存在**：厂商 U-Boot 的 tftp+bootm 已实证。新 U-Boot 可以包成
   uImage 从 RAM 链式启动（U-Boot-in-U-Boot），**全程不写 flash**；DDR 初始化也可
   复用（链式启动继承已初始化的 DRAM，跳过最难的一段）。什么时候它能在 RAM 里完成
   「读 flash + 网口收发 + 起内核」全链，什么时候才谈刷进 mtd1。
3. **源码可得**：U-Boot 2013.04 是 GPLv2，中兴有义务提供源码；厂商固件自带泄露路径
   /zte/csp/opensource/（docs/原厂加速方案逆向-2026-10-28.md:83 已经为内核规划了
   同一条 GPL 索取路线，U-Boot 可以搭同一班车）。ZXIC SDK 渠道与 cnjn 生态是备选。

## 4. 风险与护栏

- **mtd1 是全机唯一真砖点**。当前所有升级路径（fwslot、sysupgrade、e2631-upgrade）
  都刻意不碰它（bootIncl==0），这是本移植最值钱的一条设计。刷自定义 U-Boot = 第一次
  打破这条线。
- `backup header!!` 的冗余头机制语义未验，不能假定它是自动恢复网。
- 硬件兜底存在：SPI-NAND 128MB（WSON8）可用 NAND 编程器拆机救回，但未实测。
- 护栏（照搬本项目既有纪律）：RAM 链式全链验证前绝不写 flash；写 mtd1 必须走用户
  批准 + 先完整回读校验 + 保留原厂备份；一切构建走 CI。

## 5. 建议路线（分阶段，每阶段独立有价值）

- **P0（0 成本，今天就做）**：把「串口控制台 tftp+bootm」固化为文档化救砖手册
  （docs/01-情报汇总与事实核验-2026-10-13.md:113-118 已有全部素材）；当前 e2631-fwslot
  + failsafe 已经是恢复价值的大头。
- **P1（低成本，值得排期）**：发 GPL 索取（U-Boot 2013.04 + cspkernel4.1 一起要）；
  拿到源码后逆向 mtd1 引导区格式（bootheader/secondboot/备份头语义）。
- **P2（中等，概念验证）**：RAM 链式启动自研/上游 U-Boot（先只跑通串口+内存，零驱动
  移植压力），验证「换 U-Boot」这件事本身不触雷。
- **P3（重活，周~月）**：移植 SPIFC(0x94406000) 读 flash + GEPHY/mdio 网口驱动 →
  TFTP 服务端 → 有条件再做 Web 界面。
- **P4（终态，需用户批准）**：谨慎写 mtd1 的路径设计（双份引导区 + 回退验证）。

## 6. 与本轮工作的关系

不影响正在跑的 RUN1/RUN2 parity、刷机验收与修复队列。若采纳，建议作为**独立 goal**
在主线质量整改之后排期；P1 的 GPL 索取函可以现在就起草（只读动作，随时可做）。
