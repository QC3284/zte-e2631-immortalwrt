# E2631 多功能 U-Boot 设计（E4：DHCP + Web 救援）— 2026-11-27

状态：设计稿（未实现、未刷机）。上游依据：
`evidence/e4-bl-mt798x-dhcpd-study-20261127.md`（事实、尺寸、复用判定）。
本文件给需求、A/B/C 方案对照、v1 最小救援规格、预算、刷写路径、验收与门槛，
供 Lead/用户拍板后进入实现任务（E4-实1）。

## 0. 一页结论

- **v1 = 方案 A（最小救援）**：串口命令 `e2631rescue` 进入 → lan1 上起 DHCP 服务器 +
  单页 HTTP → 接收一个 mtd0 镜像（655,360 B）→ 校验 → `e2631flash` 五步写入
  `0x20000..0xC0000` → 重启回槽。估算 **16–34 KB（中位 ~25 KB）**，在现有
  159,104 B 基线余量内，不需要砍 EFI/FAT/MMC/bootstd。
- **正常上电行为不变**：不做自动救援、不做按键手势；启动计数自动进入属 E5，不在 v1。
- **上游可复用的只有核心栈**（TCP/HTTP/DHCP + gzip 资源嵌入）；failsafe 高级模块与
  MTK 板级胶水必须重写（详见研究 doc §2.3）。
- **门槛**：F2（TX 不通）未修复前 E4 v1 无法验收（DHCP 租约、网页、上传都要求回包）。
- **决策待用户**：是否只做 A；是否捐 EFI/FAT/MMC/bootstd（B 才必需）；是否要 TFTP
  第二通道；上传缓冲地址需实测复核；网页刷机要求串口可用（安全前提）。

## 1. 需求（Lead m04028，本设计必须逐条满足）

### MUST（v1 必须）

1. **正常上电行为不变**：`e2631boot` 在 3 s 窗口内自动起选中槽；v1 永不自动进入
   救援模式。
2. **救援入口 = 串口控制台命令**（`e2631rescue`，或 `e2631net rescue` 子命令）。
   本板无用户按键，**不设计按键手势**。启动计数触发是 E5，不是 v1。
3. **救援模式**：lan1 上做 **DHCP 服务器**；提供**一个最小 HTTP 页面**，只接收**一个
   固件 blob（mtd0 镜像）**，显示上传进度，然后走 **e2631flash 五步**（erase → all-FF
   verify → write → read back → compare）刷写，并重启进槽。**不要求 host 侧
   DHCP/TFTP 服务器**。
4. **写前校验**：magic / 几何 / 头 CRC / 大小窗口；拒绝 `> 0xA0000` 的镜像；
   **绝不触碰** secondboot（0x0..0x20000）、env 块（0xC0000..0xE0000）、保留扇区
   （0xE0000..0xFFFFF）。
5. **所有失败都上报浏览器和控制台**（不允许静默返回）：DHCP 超时、HTTP 错误、
   镜像拒绝、erase/write/verify 失败。
6. **装进获批的尺寸预算**（每个方案写明假设的预算），且**新代码不依赖
   EFI/FAT/MMC/bootstd**。

### SHOULD（有余量再做）

- 可选 TFTP 第二通道（服务端）。诚实的成本：我们的 `tftp` 是客户端；要在救援模式里
  **提供** TFTP 服务端，需要复用 legacy `net_loop` 的 UDP 处理，估 2–4 KB，属
  「便宜但非零」，排在 HTTP 之后。
- 页面提供 **verify-only（只校验不写）** 模式。
- 写前在页面显示 **镜像 SHA-256** 与 **双槽表**。
  （SHA-256 由浏览器 WebCrypto 计算并显示，设备端只做 CRC32——我们当前
  `CONFIG_CMD_HASH`/`CONFIG_SHA256` 未开，见研究 doc §2.2；若要在设备端算
  SHA-256，需额外 +3–6 KB。）

### WON'T（v1 明确不做，让用户看到裁剪）

i18n、web 终端、flash 编辑器、env 编辑器、UBI 卷管理、多网口、HTTPS、EFI 启动、
文件系统浏览。

### 若 F2 未修复

救援模式**整个 v1 无用**：DHCP 需要 TX 发 OFFER/ACK，网页需要 TX 回 HTTP 响应，
上传需要 RX 收数据。F2-a 的代码修复已落地（patch 0023 诚实 TX 错误 + BMU pending-retry、
patch 0024 几何断言，24-patch 构建绿，`evidence/uboot-e2-fix-20261127.md`），但**真机零写入
复测（该文档 §5）尚未执行**；此复测 PASS 是本设计实现任务的入口条件。

## 2. 方案 A/B/C

### 2.1 方案内容

- **A 最小救援（v1 推荐）**：复用 `net/mtk_tcp.c` + `net/mtk_httpd.c` 核心 +
  `net/mtk_dhcpd.c`；新增板级 `e2631rescue`（起 eth、配 192.168.1.1、起服务循环）、
  弱钩子 `httpd_get_upload_buffer_ptr()` 返回 0x46000000、上传→校验→调
  `e2631flash 0x46000000 0x20000 0xA0000`、重启；手写单页资源（gzip 2–4 KB）。
- **C 菜单 + TFTP + Web**：A + E3 主线 `cmd/bootmenu.c` 菜单（一项
  `"Start Web failsafe" → "e2631rescue"`）+ `net_abort` UDP 触发（可选）+ DNS（可选）
  + TFTP 服务端（SHOULD）。
- **B 完整 Web UI**：A + failsafe 框架 + 重写版高级模块（env/备份/主题/控制台，
  剔 MMC/UBI/GPT）+ 完整 bootstrap 主题资源（无 i18n）。工程量与面积都上一个台阶。

### 2.3 尺寸与预算（假定值）

密度方法与推导见研究 doc §4.1–§4.4；这里的「预算」是每个方案假设可用的字节数：

| 方案 | 新代码估算 | 假定预算 | 余量 | 若超限先砍什么 |
|---|---:|---:|---:|---|
| A | 16–34 KB（中位 25） | **159,104 B**（基线，不捐子系统） | ~125–143 KB | 裁 TCP 连接数/日志、DNS、进度 JS |
| C | 22–44 KB（中位 33） | 159,104 B（可不捐；建议捐 EFI/MMC 求稳 → 289,800 B） | ~115–137 KB | 先砍 DNS/net_abort，菜单只留一项 |
| B | 85–137 KB（中位 110） | **289,800 B**（基线 159,104 + 捐献 ~130,700 linked；Lead m04017） | ~180 KB | 砍 i18n（18,468）、控制台模块、UBI/NAND raw、第二主题 |

捐献口径（Lead m04017 实测对象 `.text`）：EFI loader 100,460 + MMC 14,321 +
FAT 16,835 + PXE/bootstd/bootflow 18,604 = 150,220 B 对象，按 ×0.87 折算约
130,700 B 链接字节。A/C **不依赖**这些被捐代码；捐了只是把余量做大。

### 2.4 每个方案的「失去什么」

- **A**：没有 i18n/终端/flash 编辑器/env 编辑器/备份下载/UBI/多主题/HTTPS/EFI/FAT 浏览；
  只保留「DHCP + 一页上传 + 五步刷写 + 重启」。**不捐任何现有子系统**，因此现有镜像
  能力（若有）不减少。
- **C**：同 A + 菜单/TFTP；若为求稳捐 EFI/MMC，则失去 EFI 启动、MMC 设备与 FAT 浏览
  （本板无 MMC 设备、无 EFI 需求，实际损失≈0）。
- **B**：捐 EFI/FAT/MMC/PXE 后，救援环境只剩 DHCP + HTTP + TFTP + mtd/槽操作：
  **不能浏览文件系统、不能 USB、不能 EFI 启动、不能 PXE/bootstd 启动流**；同时
  failsafe 高级模块要按我们的 flash/env 模型重写。

## 3. 推荐路线

1. **E4-实1（v1）= A**：先修 F2，再做 A；验收后再按预算加 SHOULD 项。
2. **E3 菜单并行**（代码独立，4–7 KB）：A 绿之后加菜单项，或与 A 并行落地后只做一行集成。
3. **C 的 TFTP/net_abort**：A 绿且用户要「无浏览器也能救」时再加。
4. **B**：只有用户明确要完整 Web UI、且批准捐子系统与重写工期（估 ≥1–2 周）才启动。
5. 启动计数/失败自动进入：E5，独立设计（依赖 env 写回与计数语义，不在本文件范围）。

## 4. v1 最小救援规格（A 一页版）

### 4.1 入口与状态机

```
正常上电 → e2631boot（3 s 窗口，行为不变）
serial "=>" 输入 e2631rescue
  → eth 初始化（E2 驱动；失败则打印并返回 shell）
  → 打印：MAC / ipaddr 192.168.1.1 / DHCP 池 192.168.1.100 起 / "DHCP+HTTP on lan1"
  → 阻塞服务循环（DHCP + HTTP:80；Ctrl-C/串口键退出 → 返回 shell）
网页 POST /upload（唯一入口）
  → 收 655,360 B（或多段但总长必须等于 655,360）
  → 校验（RAM 内，失败立即 4xx/文本 + 串口）
  → 页面显示 "erasing → blank → writing → reading → comparing"
  → e2631flash 五步（失败逐块报错并保持命令行）
  → 成功：页面 + 串口显示 CRC32/耗时；"reboot" 按钮 → reset → e2631boot 起槽
```

### 4.2 HTTP 端点（最小集）

| 方法/路径 | 作用 | 失败码 |
|---|---|---|
| `GET /` | 单页（gzip，含上传表单/进度 JS） | — |
| `POST /upload` | 接收唯一 mtd0 镜像 | 400 大小/magic/几何；409 忙；500 flash 失败 |
| `GET /status` | 返回阶段（idle/validating/erasing/blank/writing/reading/comparing/ok/error） | — |
| `POST /reboot` | 成功后才允许；`do_reset()` | 409 未成功 |
| `POST /verify`（SHOULD） | 只校验不写 | 400 同 upload |

进度：上传阶段用 Content-Length 分块计数；写阶段用 e2631flash 现有逐块打印/回调。
页面显示：文件 SHA-256（浏览器 WebCrypto）、大小、magic、载荷长度、目标 0x20000、
槽表（slot0/slot1 serial/version）、当前阶段、结果。

### 4.3 校验清单（写前，全部 RAM 内）

1. 总长 == `0xA0000`（655,360）；
2. 镜像 +0x10 的 u32 == `0x73383231`（"128s"）；
3. 镜像 +0x14 的载荷长度 `0x800..0x9F800` 且 `0x800+len ≤ 0xA0000`；
4. 头块 0x800 B CRC32（我们自己的校验；vendor digest 是非安全 strap，不验）；
5. 目标固定 `0x20000`，长度固定 `0xA0000`；网页不能传 offset/len；
6. 拒绝空文件、`>0xA0000`、非 0xA0000。

### 4.4 写入与禁区

- 调 `e2631flash`（可直接调用其 core 函数或 `run_command`，实现时二选一但都走同一
  五步实现）写 `0x20000`，`len=0xA0000`；
- **不触碰**：secondboot `0x0..0x20000`、env `0xC0000..0xE0000`、保留区
  `0xE0000..0xFFFFF`（secondboot/env 由 e2631flash 硬拒，保留区由固定写区保证不触及）；
- 失败路径：erase 失败 / 擦后非 0xFF / write 长度不符 / readback CRC 不符 / compare
  不符 —— 每一种都返回页面错误文本 + 串口打印，并**不执行 reset**。

### 4.5 安全前提

网页刷机前串口必须可用（有我们的 U-Boot 串口控制台）；host 保留原 mtd0 镜像与 sha256。
掉电窗口（640 KiB 擦写）与回滚说明见研究 doc §5.3。

## 5. 行为合同（v1）

1. 正常上电：3 s 窗口内自动 `e2631boot`；**不初始化网络、不进救援**。
2. 救援：仅串口输入 `e2631rescue`；进入后 lan1 上 DHCP 服务器 + HTTP:80。
3. 退出：串口按键/命令（例如 Ctrl-C 或 `exit`）返回 U-Boot shell；设备不自动重试。
4. 刷写成功：页面/串口双报成功（CRC32、耗时、写区段）；**不自动重启**，`reset` 命令当前是占位实现（patch 0003 只打印提示，task-76 修复），可靠路径是断电重启（拔电再上电）。
5. 刷写失败：停在 U-Boot shell/救援模式，页面与串口同时报错；不自动重启、不自动重试。
6. 返回 Linux：断电重启（拔电再上电）；页面的“完成”文案不得把 `reset` 当可靠路径。
7. 上传带 `X-E2631-SHA256`（整个 655,360 B 文件）；设备在擦除前校验并回显 `sha256=`/`sha_match=`；页面在摘要一致前不启用“写入待命”。
8. 不做：自动进入、按键手势、启动计数触发（E5）、多网口、HTTPS、i18n、EFI/FAT/MMC 依赖。

## 7. 依赖、风险、门槛

- **F2（阻塞）**：patch 0023/0024 的代码修复已绿（`evidence/uboot-e2-fix-20261127.md`），
  但零写入真机复测（§5）尚未执行；复测 PASS 前不进入实现验收。见研究 doc §6 与
  `evidence/e2-session-failure-analysis-20261122.md`。
- **F1（边界）**：刷完自动起槽若 `bootm` 静默返回，页面必须显示失败（串口可见），
  不能假装成功；产品级 flash boot 目前绿的，但要显式处理。
- **上传缓冲**：0x46000000 + 1 MiB 需在目标镜像上用 `bdinfo`/`mem_map`/`md` 复核，
  与 e2631flash 的 net DMA arena（0x45000000–0x45FFFFFF）不重叠。
- **API 漂移**：2027.01-rc2 缺 `net_set_udp_handler` 等 helper，需 compat shim
  （估 1–3 KB；研究 doc §2.2）。
- **许可**：上游 GPL-2.0，保留版权/SPDX；我们新文件用 GPL-2.0+。
- **预算**：A 用基线余量即可；若 Lead 决定捐 EFI/FAT/MMC/bootstd，先落 CI 守卫与
  `UBOOT-INFO.txt` 的预算记录，再开工 B。
- **安全**：网页刷机=第一次「无串口也可尝试」的写 mtd0 通道；v1 坚持「串口可用」
  前提并在页面显著提示。

要点（细节以上述文件为准）：

- **端点**：`/flash`（v1 bootloader 写，**保持不动**）、`GET /status`（v1 键保留 + 追加 op/slot/guard/bytes/槽字段）、`GET /slots`、`GET /env`（只读）、`GET /backup`（mtd0 `0x20000..0xC0000` 655,360 B + CRC32/SHA-256 头）、`POST /firmware?mode=validate|write&slot=auto|0|1`、`POST /boot?slot=0|1`（RAM 覆盖，仅本次）、`POST /factory?confirm=reset`（擦 `rootfs_data`）。
- **写路径所有者**：bootloader = `e2631flash`；firmware slot = 新增 `e2631fwslot`（语义对齐 Linux `e2631-fwslot`，golden 向量对拍）；overlay = 新增 `e2631factory`（只擦按名核对的 `rootfs_data`，无文件系统逻辑）；env = `e2631env` 白名单写（页面不暴露）。**禁止第三个固件槽写入实现**。
- **固件写语义**：目标默认 `next_slot`（serial 最大）；校验顺序/守卫/擦整槽/写 body/写版本头（serial=max+1、`H_NEW=1`、CRC2 重算）/回读校验/失败擦头回退，逐条对齐 `e2631-fwslot`；**只拒绝重写“identity=vendor 且 intact”的完整原厂槽**，UNKNOWN/损坏/无头的槽可写（救砖）；另一槽 identity=ours 时 `guard=weak` 并页面警示。**验收不做同一镜像牺牲写**：先做 validate+负例+净零 bootloader，首次真实固件升级（新镜像）走 `/firmware` 作为验收，需用户批准。
- **RAM**：`/firmware` 上传暂存 `0x46100000`，上限 `0x1BE0000`（槽跨度 − 一个擦除块）；不改现有 0x40008000/0x42000000/0x44000000/0x45000000/0x46000000/0x47F00000 布局；新增编译期断言。
