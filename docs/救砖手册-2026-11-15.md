## 0. 先记住三件事

1. **全机唯一的真砖点是引导区**：我们的 mtd0（flash 0x0–0x100000），里面是 secondboot + U-Boot + 环境区（env）。它坏了只能上编程器（未验证）。除此以外——包括两个 28 MiB 系统槽、身份区、配置区——在引导区完好的前提下都有恢复路径。
2. **现行所有升级路径都不写引导区**：包内 `bootIncl == 0`（docs/architecture.md:82；tools/mkfactory.mjs:167），所以在线升级、原地重刷、槽位切换失败最多是"系统起不来"，不是砖。
3. **恢复顺序从便宜到贵**：系统还能起（failsafe / SSH）→ U-Boot 控制台（串口 + TFTP RAM 引导）→ 原厂槽位 / 原厂 Web 页 / 原厂侧通道 → 编程器。**不要一上来就拆机刷 NAND。**

### 0.1 判断"卡在哪一层"

| 最远看到的现象 | 卡在 | 去读 |
|---|---|---|
| 串口完全无输出 / 只有乱码 | 串口链本身，或 ROM/secondboot 没跑 | §1 → §6.4 |
| 有 `Boot SPI NAND`…`Jump` 但**没有** `U-Boot 2013.04` | secondboot / U-Boot 映像 | §6.4（编程器；先排除串口问题） |
| 有 `U-Boot 2013.04`、`*** Press 1 ...`、`cspboot:1475 Booting image` 后停住 | 槽头 / 内核加载 | §4（控制台）→ §5（槽位） |
| 有 `Starting kernel ...` 但**没有** `init: - preinit -` | 内核 / DTB / 启动参数 | §4（RAM 内核交叉验证）→ §5（回其他槽） |
| 到 `init: - preinit -`、failsafe 提示之后死 | rootfs / overlay / 配置 | §3（failsafe） |
| 系统起了，但 SSH / 密码 / 网络坏 | 配置层 | §3 |
| 两个槽都起不来 | 两个系统槽 | §5（原厂 Web 页 / 原厂侧通道） |

## 1. 串口：一切恢复的前提

### 1.1 硬件与连线

- 板载 UART 排针 **X1A22**，3.3 V TTL 电平，115200 8N1（docs/refs-local/ZX279128S-适配现状-2026-10-12.txt:57）。
- 针序：Pin1 = VCC（**不接**）、Pin2 = TX、Pin3 = RX、Pin4 = GND。主机 TX 接针 3，主机 RX 接针 2（交叉），GND 共地。
- 本会话用的 USB-TTL 是 CH343（`1a86:55d3`，DKMS V2.2），枚举为 **/dev/ttyCH343USB0**（不是 ttyUSB*）。证据：evidence/cold-boot-sampling-20261114.md:15。
- 只看日志：最少接 GND + 设备 TX → 主机 RX。要发命令（failsafe 的 `f`、U-Boot 密码、sysrq）必须把主机 TX 也接上。

### 1.2 单读者原则（最容易踩的坑）

串口是独占资源，同一时刻只能有一个读者。本机长期跑采样链（flock 保护）。手工交互前**先停采样链**，否则你敲的字符会被采样进程抢走，或你的输入看不到回显。

```bash
pgrep -af "capture-supervisor|serial-bootwatch|capture-stallwatch"
pgrep -af "^cat /dev/ttyCH343USB0$"
fuser /dev/ttyCH343USB0          # 有输出说明还有进程占着
```

采样链恢复（主机或 DSH 重启后必须重跑，脚本目录 /home/qc233/zte/e2631-capture/）：

```bash
cd /home/qc233/zte/e2631-capture
setsid nohup ./capture-supervisor.sh >>/tmp/e2631-capture-supervisor.out 2>&1 </dev/null &
setsid nohup node ./serial-bootwatch.mjs >>/tmp/e2631-bootwatch.out 2>&1 </dev/null &
setsid nohup ./capture-stallwatch.sh >>/tmp/e2631-capture-stallwatch.out 2>&1 </dev/null &
```

- 采样日志：/home/qc233/zte/e2631-serial-boot.log；事件：/home/qc233/zte/e2631-serial-capture-events.log。
- supervisor 每 5 s 检查并续 `cat`；任何"另一个 cat 已经在读"都会被 flock 挡住。
- 设计说明与 19 次冷启动记录：evidence/cold-boot-sampling-20261114.md:15-23、200-233。

## 3. 路径 A：系统还能起 → failsafe / 系统内命令

### 3.1 failsafe 进入（实测）

- 时机：内核启动到 preinit 阶段。本机实测约 2.5 s 出现 `init: - preinit -`、7.7 s 出现 failsafe 提示，所以**看到 `Press the [f] key and hit [enter] to enter failsafe mode` 就连续狂按 `f`**（带回车也行；脚本每 0.25 s 发一次 `f\n`）。
- 成功标志：`- failsafe -` → BusyBox ash → `================= FAILSAFE MODE active ================` → 提示符 `root@OpenWrt-failsafe:/#`。
- 进入后会提示两个专用命令：`firstboot`（恢复出厂设置，清 overlay）和 `mount_root`（挂载 rootfs 及其配置）。
- 失败常见原因：按晚了（已经进正常启动）、串口被别的进程占着（§1.2）、波特率不对。按晚了就断电重上电重来——这一步不写 flash，零风险。
- 证据：/home/qc233/zte/e2631-serial-recovery-1.log（7.686 s 提示、`- failsafe -`、failsafe 横幅）；TEAM-NOTES.md 历史记录。

### 3.2 failsafe 标准修复流程

```sh
mount_root                      # 必须：挂载 rootfs + overlay，之后改的才是持久配置
# 例 1：密码坏了 / 清空 root 密码（2026-11-14 实战用过的）
printf 'root::0:0:99999:7:::\n' > /etc/shadow
# 例 2：网络配置坏了
vi /etc/config/network
# 例 3：想整体恢复出厂（丢 overlay 配置）
firstboot
sync
reboot -f
```

- 实测日志：/home/qc233/zte/e2631-serial-recovery-2.log（mount_root → overlay 挂载 → 改 shadow → grep 确认 → sync → reboot -f，随后完整正常启动）。
- 吓人但无害的输出：`overlayfs: upper fs does not support tmpfile.`、jffs2 的 CRC 警告（历史脏数据）。只要 `mount_root` 成功、`mount | grep overlay` 能看到 `/dev/mtdblock8 on /overlay type jffs2`，就能改。
- failsafe 本身**不写 flash**，改的是 overlay（jffs2）。写坏了最坏情况是丢配置，不会砖。

### 3.3 串口 sysrq：内核活着但 SSH 锁死 → 软重启（实测）

- 现象：系统还在跑（串口有输出、可能能 ping），但 SSH 全废（密码错误、连空密码都不行），难道只能断电？
- 做法：串口发 **BREAK**，随后发 `b`（magic sysrq 立即重启）。脚本实现：`termios.tcsendbreak(fd, 0)`，再在 0.4 s 与 1.4 s 各发一个 `b`（/home/qc233/zte/e2631-serial-recovery.py:13-19）。
- 前提：内核开了 `MAGIC_SYSRQ=y` + `MAGIC_SYSRQ_SERIAL=y`（本机 sanechips config 已开，2026-11-14 密码事故即用此招重启，实测可用；TEAM-NOTES.md:188）。
- 内核已经挂死时无效——那时走 §4 控制台或断电。

### 3.4 能登录时：系统内命令（写 flash 的步骤需批准）

| 命令 | 作用 | 写 flash |
|---|---|---|
| `e2631-fwslot info` / `info -j` | 查看两槽身份/serial/CRC | 否 |
| `e2631-fwslot check <pkg.bin>` | 只校验包，不写 | 否 |
| `e2631-fwslot upgrade-check` | 原地升级前置条件自检 | 否 |
| `e2631-fwslot switch` | 校验另一槽并把它设为下次启动 | 只写目标槽头 128 KiB |
| `e2631-fwslot boot <0\|1>` | 同上，显式指定槽 | 同上 |
| `e2631-fwslot upgrade <pkg.bin>` | 原地重写**当前运行槽**（要求另一槽有完整原厂镜像兜底） | 是 |
| `e2631-fwslot install <pkg.bin>` | 写**另一槽**（另一槽是原厂/身份不明时默认拒绝，需 `--replace-other-system`） | 是 |
| `e2631-upgrade` | 在线升级（GitHub Releases 通道） | 是（内部走 fwslot/sysupgrade） |

- 命令语义原文：树 fork package/e2631/e2631-fwslot/src/e2631-fwslot.c:1403-1421；槽位判定与安全设计见同文件 :1-53。
- `--no-fallback-check` / `--replace-other-system` 是"我确定不要兜底"的开关，只在明确知情时用（条款见 fwslot.c:31-46、915-928）。
- 系统升级（LuCI / sysupgrade）内部就是 fwslot 的 upgrade/install 路径；失败后仍可用同一命令重刷。
- 重刷槽会**重建 rootfs_data（overlay）**：配置、密码、已装插件都清空（docs/02:938 有刷槽把坏 hook 一起清掉的实战记录）。刷槽前先导出要保留的配置。

### 3.5 案例：密码事故恢复（2026-11-14，实测）

1. 起因：远程 shell 双引号展开把 `$5$` 开头的密码哈希写坏 → SSH 全部拒绝，包括空密码。
2. 串口看到系统还活着 → `BREAK` + `b` 重启（§3.3）。
3. 重启时狂按 `f` 进 failsafe（§3.1）。
4. `mount_root` → `printf 'root::0:0:99999:7:::\n' > /etc/shadow` → `sync` → `reboot -f`（§3.2）。
5. 系统正常启动，root 空密码，立刻设新密码。

## 4. 路径 B：系统起不来，但 U-Boot 能起 → 控制台 + TFTP RAM 引导

### 4.1 进 U-Boot 控制台（实测，注意密码坑）

1. 上电，串口看到 `*** Press 1 means entering boot mode***`，**在倒计时内按 `1`**。
2. 随后：`cspboot:1454 Entering boot mode ...` → `*** Please input bootmode password: ***`。
3. 密码：`5cE080@fyBD`（注意：与同平台 H3600 的 `Boot4128s` 不同；docs/refs-local/ZX279128S-适配现状-2026-10-12.txt:302）。
4. **必须以 `\r`（CR）结尾，不能是 `\n`。** 用 picocom/minicom 敲回车没问题；用脚本必须显式发 `\r`。本机事故：发 `\n` 后只回显 11 个星号、密码不被判、设备卡在密码提示（SSH 也进不去）。自救：再发一个 `\r` 把缓冲区当输入提交 → `passwd is too long,input passwd = 5cE080@fyBD`（或 `passwd is error`）→ 重新提示 → 输正确密码 + `\r`。证据：/home/qc233/zte/e2631-uboot-console.log:107-108、console2.log。
5. 进入后看到 `Hit 1 to upgrade software version`，再 `Hit any key to stop autoboot: 3 2 1 0`，按任意键停在 `=>`。`Unknown command 'autorun' - try 'help'` 是正常现象（env 里没有 autorun 命令），不是错误。

### 4.2 控制台里能做什么

实测 `help` 输出共 **43 个命令名**（TEAM-NOTES 记 44，以实测为准）：

```text
?  base  bdinfo  boot  bootd  bootk  bootm  bootz  cmp  coninfo  cp
cspboot  cspnand  cspnor  cspstart  dhcp  echo  fdt  go  gpiotest  help
i2c  imxtract  itest  md  mii  mt  mtddebug  mtest  mw  nand  ping
printenv  reset  run  saveenv  setenv  sleep  tftp  upgrade  version
watchdog  xmodem
```

- 常用：`printenv`（看 env）、`tftp` + `bootm`（§4.4）、`md`/`mw`（看/改内存）、`version`、`reset`（正常重启）。
- env 默认值对我们有利：`ipaddr=192.168.1.1`、`serverip=192.168.1.100`、`netmask=255.255.255.0`、`loadaddr=0x42000000`（docs/U-Boot结构分析-2026-11-15.md 环境表；RE 证据 §Q3）。
- **不要在控制台里 `saveenv`**（会把 env 写回 mtd0 引导区；本次恢复不需要）。
- **不要碰 `upgrade` / `nand` / `cspnand`**：它们能写 flash，但语义与参数未验证（§10），救砖时禁用。

### 4.3 安全离开

- 用 **`reset`** 恢复默认启动链（实测）。
- **不要用 `boot`**：实测 `boot` 只执行 bootcmd（即 setenv bootargs）然后回到 `=>`，不会启动系统（/home/qc233/zte/e2631-uboot-console2.log）。
- **不要按 `1`** 去响应 `Hit 1 to upgrade software version`：那是原厂升级模式，未验证，可能直接写槽。控制台里要"按任意键停 autoboot"，按空格或其他键都行，别按 1。

### 4.4 TFTP + bootm：零写 flash 的 RAM 引导（机制已验证，组合待演练）

前提：一台 PC 网线直连设备 LAN1，PC 静态 `192.168.1.100/24`（正好等于 U-Boot 默认 `serverip`，所以**不需要 setenv**）。

1. 准备 TFTP 服务（本机已有 dnsmasq，不用另外装 tftpd）：

```bash
mkdir -p ~/e2631-tftp && cp <initramfs.uImage> ~/e2631-tftp/
sudo dnsmasq --no-daemon --port=0 \
  --interface=<直连网卡> --bind-interfaces \
  --enable-tftp --tftp-root=$HOME/e2631-tftp
# --port=0 关掉 DNS，只留 TFTP；防火墙放行 UDP 69
```

2. U-Boot 控制台（§4.1）里执行：

```text
ping 192.168.1.100
tftp 0x43000000 <initramfs 文件名>
bootm 0x43000000
```

3. 成功标志：`## Booting kernel from Legacy Image at 43000000` → `Starting kernel ...` → 进入 ImmortalWrt。这是 RAM 系统：无 overlay，重启即消失，**不写 flash**。

- **地址规则**（踩过坑）：TFTP 下载地址固定 **0x43000000**；不能填镜像的 load/entry 地址 0x48008000——uImage 的 64 B 头会盖住内核入口，表现为静默崩溃（docs/refs-local/E2631适配开工路线-2026-10-12.txt:187-191）。
- 为什么内核 load 是 0x48008000：U-Boot 的以太网缓冲在 0x41000000、free-buffer list 在 0x41800000，内核解压到 0x40008000 会踩它们（表现为 RX/TX 一起锁死）；RAM 型系统因此改用 0x48008000（树 fork target/linux/sanechips/image/Makefile:14-29）。
- 机制实证：2026-10 真机用 `tftp 0x43000000` + `bootm 0x43000000` 成功引导 12.7 MiB mainline uImage 到 busybox shell（docs/01:112-118）。

### 4.5 ⚠ 当前缺口：CI 不产出 initramfs.uImage（用 §4.4 之前先补这个）

- 构建配置会生成 initramfs：树 fork seed/e2631.config:9 `CONFIG_TARGET_ROOTFS_INITRAMFS=y`；命名 `...-initramfs.uImage`（树 fork target/linux/sanechips/image/Makefile:44-45）。
- 但套件 .github/workflows/firmware.yml 只上传 `build-logs/` 和 `release/`（:191-199），`release/` 里只放打包好的 factory bin + SOURCE-INFO（:122-124、:161）——**没有收集 initramfs.uImage**。
- 本机也没有现成的 initramfs.uImage（/home/qc233/zte/e2631-t5-artifacts 只有 factory bin）。
- 结论：TFTP RAM 引导的机制已被 2026-10 的 mainline 镜像验证，但**当前 CI 产物无法直接用于恢复本项目系统**。修复建议（一行 CI 改动，归 CI 负责人）：把 `bin/targets/**/immortalwrt-*-initramfs.uImage` 复制进 `release/`，或作为独立 artifact 上传。在补上之前，§4.4 只能当机制演练，不能当实战恢复手段。

### 4.6 进了 RAM shell 之后能做什么（未演练，谨慎）

- RAM 系统里 `e2631-fwslot` 在 `/sbin`（包里预装，树 fork seed/e2631.config:11），槽位分区也在 DTS 里，理论上可以直接：
  - `e2631-fwslot info` 看两槽；
  - `e2631-fwslot boot 0` 把原厂槽设为下次启动，再 `reboot -f`；
  - 或从 PC 下载包后再 `e2631-fwslot upgrade /tmp/pkg.bin`（RAM 里空间有限，包约 20 MB，先确认 tmpfs 余量）。
- 这些组合**未实测**（目前只验证到"TFTP+bootm 能进 mainline busybox"）。第一次实战先只读检查（`info` / `check`），确认无误再写；写之前仍需用户批准。

## 5. 路径 C：两槽都起不来，或要回原厂

### 5.1 先理解槽位选择（决定你还有没有救）

- cspboot 扫全片（每 128 KiB 找槽标记/内层 magic），**只校验版本头 CRC1**（覆盖 [0x00:0xa4]，不含 serial）；选择 **CRC1 有效且 serial 最大**的槽，相等时选 slot0（树 fork fwslot.c:5-11；docs/02:82-91；启动日志 `pdt_getimg select = 1, serial0=0x7, serial1=0x9`）。
- 故障分两类（实测，docs/02:358-368）：
  - **类 1：CRC 层坏**（内核/rootfs CRC 不对、包内容坏）→ cspboot 把该槽判无效、**自动换另一个槽**；串口会打 `not found vaild fs!!` 和 `Total found 2 firmwares(valid:1), start from ver 0`。这类**不需要串口**。
  - **类 2：内核能起但之后挂死**（驱动/配置问题）→ **不会自动换槽**：选槽只看 serial，没有"启动失败计数"（pdt_getimgindex 只比 serial）。反复断电重上电仍是同一个槽。这类必须串口/U-Boot 控制台（§4）或从原厂侧重写（§5.3 / §5.4）。
- ⚠ 老说法"断电重上电 2~3 次就自动回退"**只对类 1 成立**，别拿它当类 2 的救命稻草（docs/02:368）。

### 5.2 回原厂：`e2631-fwslot switch`（实测，最省事）

- 前提：当前系统能跑（SSH 或串口登录）。
- 做：`e2631-fwslot switch` → 校验目标槽头里的 CRC → 只把目标槽版本头改写成更高 serial（CRC1 不含 serial，所以不会破坏有效性）→ `reboot`。
- 结果：下次启动进原厂系统，**原厂固件 body 一个字节没动**（fwslot.c:20-23）。
- 之后回 ImmortalWrt：§5.4（stage.mjs）或 §5.3（原厂 Web 页刷 factory.bin）。
- 注意：`switch` 只写目标槽头部 128 KiB，不碰引导区、身份区。

### 5.3 原厂 Web 升级页（浏览器手动；写非运行槽，整槽替换）

- 前提：能进原厂系统；知道**原厂 Web 登录密码**（≠ telnet root 密码，也不在备份里；docs/02:327）。
- 步骤：
  1. 浏览器打开 `http://<设备IP>/supgrade.html`（该页面可无登录打开——登录框被隐藏，docs/01:196-221）。
  2. 选择我们的 repacked 包 `e2631-immortalwrt-factory.bin`（2026-10-14 实证用的是旧名 `out/e2631-openwrt-gen1.bin`，20,972,052 B；新名以 host/release.mjs 默认输出为准）。
  3. 提交，等页面轮询（`upgrade_firmware_query`）并自动重启。
- 实测：2026-10-14 真机走该页刷入我们的包成功，刷完运行槽 serial 升到 34，原厂槽 body 未动（docs/02:322-341、856-858）。
- 限制：页面本质是把文件 POST 到 `/?_type=hiddenData&_tag=firmware_upgrade`（字段 `VersionUpload` + `TOKEN_UPLOAD` 会话 token），登录是 JS 里的 RSA + salt（salt 在 Cookie）——**能手动用，不好脚本化**；并且不能保证 Web 侧不做额外包校验。原厂固件只暴露每槽前 3.25 MiB 的 MTD 视图，所以这条路径必须靠原厂自己写。
- 适用：两个槽都能起但 ImmortalWrt 槽坏、或想彻底回原厂。写的是**非运行槽**（A/B 机制保持运行系统不动）。

### 5.4 原厂侧通道：telnet + stage.mjs（实测）

- 前提：原厂系统能跑、LAN 可达 PC、知道 telnet root 密码（环境变量 `ZTE_TELNET_PW`）。
- PC 侧（套件仓库根目录）：

```bash
node tools/stage.mjs put          # 只读：回显设备信息
node tools/stage.mjs flash --yes  # 写入非运行槽（默认 HOST 192.168.5.3、PC 192.168.5.5:8000）
```

- 原理：原厂系统 `/var/tmp` 是 tmpfs，stage 通过 telnet 在设备上执行擦/写，把镜像塞进**非运行槽**并封头。实测：擦 slot B → 写 0x1000000 body → 封 slotStart=0x2300000 / serial=17 / isNew=1 → readback 校验 ok（docs/02:510-545）。
- 风险：在设备上执行写操作并依赖 telnet 密码；但只写非运行槽，不碰引导区。
- 回到我们系统后：插 LAN 线 → `ssh root@192.168.1.1` → `/sbin/e2631-probe`（docs/02:595-603）。

## 6. 引导区 / 身份区修复（高级；需用户批准，属于 P2/P4 范围）

### 6.1 env 区（mtd0 偏移 0xC0000，128 KiB）

- 格式：前 4 B = `0x3efcecaf`（即 CRC-32 小端 `AFFCEC3E`），随后是 NUL 分隔的 `key=value`，剩余 0x00 填充。
- 校验：`crc32(0, data@0xC0004, 0x1FFFC) == 0xAFFCEC3E`（标准 zlib CRC-32，RE 实测：RE 证据 §Q3）。改 env 必须重算这 4 B，否则 U-Boot **大概率**回退默认 env（坏 CRC 行为未实测）。
- 当前内容（dump 实测）：`baudrate=115200`、`bootcmd`（只做 setenv bootargs）、`bootdelay=3`、`bootfile=uboot.bin`、`bootloaderfile=bootloader.bin`、`console=ttyAMA0,115200n8`、`ethact=eth0`、`ethaddr=00:41:71:00:00:50`、`fullfile=upgrade.bin`、`gatewayip=192.168.1.1`、`hostname=unknown`、`ipaddr=192.168.1.1`、`linuzfile=vmlinuz.bin`、`loadaddr=0x42000000`、`memsize=256M`、`netmask=255.255.255.0`、`netretry=5`、`serverip=192.168.1.100`、`stderr/stdin/stdout=serial`、`versioninfo=U-Boot V1.0.0 20230828191152 ...`。
- 修复策略：不要手工拼 env 写 flash。U-Boot 里 `setenv`（内存）+ `saveenv`（写回）是唯一"官方"路径，`saveenv` 属于引导区写入（需批准）；Linux 侧写 mtd0 目前被 DTS `read-only` 挡住（§6.3）。
- env 坏了未必起不来（bootcmd 会缺、bootargs 默认值变少），串口仍能看到 U-Boot；先别急着修，观察默认启动是否正常。

### 6.2 U-Boot 控制台密码（替换摘要，P2+，未演练）

- 密码不是明文：`5cE080@fyBD` 的**无盐 SHA1** 摘要 20 B 存在 U-Boot 文件偏移 **0x61F80**（运行时 0x47F41780），最大长度 16（RE 证据 §Q4；docs/U-Boot结构分析-2026-11-15.md 附2）。
- 换密码 = 改这 20 B + 写回 mtd0（P2 改引导区工程的一部分，需用户批准 + 严格校验）。
- 忘了密码不能靠猜；但**串口 failsafe（§3）和系统内 fwslot（§3.4）都不需要 U-Boot 密码**——密码只是进控制台的门槛，不是救砖必需。

### 6.3 mtd0 / mtd1 / mtd2 写权限现状

- 现役 DTS：mtd0 bootloader、mtd1 tag 标 `read-only`（树 fork dts:362-371）；mtd2 wifi 未标只读，但属于校准数据，别写。
- 想在 Linux 里写引导区/身份区，必须先改 DTS 去掉 read-only（P4 范围），且仍要用户批准。
- **本手册所有救砖路径都不需要写 mtd0/mtd1/mtd2。** 真怀疑引导区坏了 → §6.4。

### 6.4 硬件最后手段：SPI-NAND 编程器（未验证）

- 芯片：FSNAND F35SQA001G，128 MiB SPI NAND，WSON8 封装（启动日志与 docs/多功能U-Boot可行性-2026-11-14.md:63-69）。
- 需要：WSON8 夹子/焊接、支持该芯片的编程器（注意 1.8/3.3 V 电压）、以及本机分区级 dump 作对照。
- 现状：**回写未验证**（没在实机上拆焊回写过）。2026-11-20 已用有效的整片 dump 做完芯片级布局实测与写回偏移表（§6.6）。风险：拆焊损坏、坏块管理/ECC 参数不对导致写回后仍不能启动。
- 原则：最后手段；动手前先另做全片备份、确认电压、由用户决定。原厂插件区 0x6e00000–0x7f00000 别当"补全备份"去碰（它不在我们的分区表里；整片回写时的注意事项见 §6.6）。

### 6.5 `backup header!!` 不是错误

- 串口在 `Jump` 前打印 `backup header!!`，是 secondboot 把 U-Boot 镜像头备份到 RAM 再跳转的**正常动作**（RE 证据 §Q1）。看到它说明引导链在正常工作。
- 同理 `non secure boot` / `non secure uboot` 表示走的是非安全启动路径（实测没有签名/CRC 校验门——这也是自定义 U-Boot 可行（P2）的前提）。

### 6.6 芯片级恢复：整片 dump 与写回偏移表（2026-11-20 实测）

2026-11-20 拿到有效的整片 dump（编程器读取、双读校验）：/run/media/qc233/DATA/zxhn_e2631_full-v2-ECC.bin（134,217,728 B = 128 MiB 数据视图，sha256 `4a20e6931808018a63378a7d630c3742bb49330441b996d3f4da690a2884b1fc`）与 /run/media/qc233/DATA/zxhn_e2631_full-v2-RAW.bin（138,412,032 B = 65,536 × 2,112 B）。完整实测记录：evidence/chip-level-layout-20261120.md。

⚠ 两份 dump 的 64 B spare/OOB **全部是 0xFF**（编程器只导出了主区）：dump 里没有真实 ECC，也没有坏块标记。

#### 6.6.1 分区 ↔ 芯片偏移（实测）

| mtd | label | 芯片偏移 | 大小 | 当前内容 |
|---|---|---|---|---|
| mtd0 | bootloader | 0x0000000 | 1 MiB | secondboot + U-Boot + env（env 在 +0xC0000） |
| mtd1 | tag | 0x0100000 | 1 MiB | 原厂身份 / MAC / 工厂数据 |
| mtd2 | wifi | 0x0200000 | 1 MiB | 原厂 WiFi 校准 |
| mtd3 | usercfg | 0x0300000 | 2 MiB | 原厂用户配置（JFFS2） |
| mtd4 | defcfg | 0x0500000 | 2 MiB | 原厂出厂配置（JFFS2） |
| mtd5 | slot0 | 0x0700000 | 28 MiB | 原厂系统槽（兜底） |
| mtd6 | slot1 | 0x2300000 | 28 MiB | 我们的运行槽（含 mtd7/8/9 别名） |
| mtd7 | rootfs | 0x2700000 | 17 MiB | = slot1 + 0x400000（squashfs + overlay 窗） |
| mtd8 | rootfs_data | 0x3360000 | 4,849,664 B | = slot1 + 0x1060000（overlay） |
| mtd9 | slot1-header | 0x3800000 | 128 KiB | = slot1 + 0x1500000（版本头在 +0） |
| mtd10 | userdata | 0x3F00000 | 47 MiB | 独立 UBI（空壳 UBIFS 卷） |

- mtd7/mtd8/mtd9 都嵌在 mtd6 里（所以分区大小之和 131.75 MiB > 128 MiB）；**整槽写 mtd6 会覆盖它们的内容**。
- 0x6E00000–0x7F00000（17 MiB）不属于任何分区：实测是原厂 JFFS2 插件/配置区（文件名明文，如 datainfo.json、uuplugin、owdpts、db_tbl_cfg.xml），我们的固件不声明也不写它；0x7F00000–0x8000000（1 MiB）为空（全 FF）。
- slot0 的原厂版本头在 slot0+0x1560000（不是我们的 +0x1500000），其 rootfs 是 AES 密文、不可解析；slot0 只能原样保存/回写。

#### 6.6.2 回写规则

1. **只写每页 2,048 B 主区**；64 B spare 必须由编程器按芯片 ECC 参数重新生成，或交给 MTD 层（nand write / ubiformat）处理。RAW 里的 spare 全 FF，**不能原样写回**。
2. **坏块**：dump 看不到坏块标记，不能"无脑整片写"；要么走坏块感知的 MTD 路径，要么写后逐块回读校验。
3. **一致性**：mtd6/7/8/9 是同一物理区的嵌套视图，必须同一时点、同一来源；不要混用 11-15 与当前的数据。mtd9 的 CRC 覆盖 kernel+squashfs 声明窗，手工拼数据必须重算版本头。
4. **地址**用 §6.6.1 的表（实测），不要按原厂 /proc/mtd 编号推算（§2.4 是抄错重灾区）。
5. **验证**：回读整片与 v2-ECC 的 sha256（`4a20e693…`）比对；分区级与 §2.3 / INVENTORY.md 的 sha256 比对。
6. **跨机禁止**：mtd0（引导区）与 mtd1（身份/MAC/工厂密钥）是本机唯一身份；整片 dump 只能回写同一台设备。
7. **门槛**：写 flash / 刷芯片必须先经用户批准；动手前先尝试再整片读一次，别拿唯一备份去赌。

#### 6.6.3 时效警告：11-15 的分区 dump 哪些还能用

| 分区 | 11-15 dump 与当前芯片 | 能否回写 |
|---|---|---|
| mtd0–mtd5 | **逐字节相同** | 可以（可作为当前备份） |
| mtd6–mtd9 | 过期（旧构建、serial 9、旧 overlay） | 不建议：回写 = 回滚到 11-15 的系统 |
| mtd10 | 过期（空 UBI、无卷） | 不建议：回写 = 退回无卷状态 |

- 当前芯片 = 11-15 之后写槽两次（serial 9 → 10 → 11）+ 重格式化 userdata 之后的状态。当前 slot1 与批量刷写 RUN3 产物的载荷逐字节相同（差异只有 overlay 和版本头 8 B：slot_start/serial/new/CRC2）。
- "当前状态的完整备份"目前只有 v2 整片 dump；分区级当前备份请从运行系统重新读（§2.1 的 sha256sum 命令）。

## 7. 危险区与禁止事项（动手前逐条确认）

### 7.1 危险分级

| 区域 | 偏移 | 破坏后的后果 | 恢复手段 |
|---|---|---|---|
| bootloader (mtd0) | 0x0–0x100000 | **真砖**：secondboot/U-Boot/env 没了 | 编程器（未验证） |
| tag (mtd1) | 0x100000–0x200000 | 丢 MAC/SSID/工厂密钥/身份 | 只能备份回写（需 P4 解锁） |
| wifi (mtd2) | 0x200000–0x300000 | WiFi 校准丢失 → 无线异常 | 备份回写（未演练） |
| usercfg/defcfg | 0x300000–0x700000 | 原厂配置丢失 | 备份回写 |
| slot0（原厂兜底） | 0x700000–0x2300000 | 失去回原厂路径 | 原厂 Web 页 / 编程器 |
| slot1（运行） | 0x2300000–0x3f00000 | 当前系统起不来 | 另一槽 / 原厂页 / stage |
| userdata | 0x3f00000–0x6e00000 | 丢数据盘，系统不受影响 | 重建 |
| 原厂插件区 | 0x6e00000–0x7f00000 | 原厂插件/配置数据（JFFS2，§6.6） | 无（不要碰） |

### 7.2 禁止事项（每条都对应历史事故或未验证风险）

1. **不要在 Linux 里写 mtd0**（当前 DTS 只读；绕过它属于 P4 范围）。
2. **不要用原厂 `fw_flashing -v switch`**：它不擦块就写，NAND 只能 1→0，标题写坏、CRC2 不一致，而且它的错误判断是反的（docs/02:92-99）。
3. **不要随手 `--replace-other-system`** 清掉原厂槽，除非你接受失去唯一兜底。
4. **不要在 U-Boot 控制台用 `upgrade` / `nand` / `cspnand` / `saveenv`**（未演练且会写 flash；救砖不需要）。
5. **不要按 `1`** 去响应 `Hit 1 to upgrade software version`（原厂升级模式，未验证）。
6. **不要在写 flash 过程中断电**（半写/坏块；虽然还有另一槽，但没必要冒险）。
7. **不要让两个进程同时读串口**（丢字符、密码输错、日志错乱）。
8. **不要相信"断电重启几次自动回退"**（只对类 1 成立，§5.1）。
9. **不要只用 ping 判断设备状态**：家庭路由器也可能回 192.168.1.1（TTL=254），看起来通了其实不是设备（docs/02:977）。
10. **任何写 flash / 刷槽 / saveenv 动作，先经用户批准**（项目硬约束）。

### 7.3 TFTP / 网络坑

- PC 直连设备 LAN1（不要经家用路由器 DHCP），PC 静态 192.168.1.100/24；确保没有别的 192.168.1.100 服务冲突。
- U-Boot 用的是 env 默认 MAC `00:41:71:00:00:50`（真实 MAC 在 tag 分区），TFTP 服务端别做 MAC 白名单。
- 看到 `T`（TFTP 超时）/TFTP error：先 `ping 192.168.1.100`，再查防火墙 UDP 69、文件名大小写、TFTP root 权限。

## 11. 术语

- **secondboot**：U-Boot 之前的一级引导（flash 文件偏移 0x0 起）。
- **cspboot**：原厂 U-Boot 里的启动逻辑（选槽、校验版本头、bootm）。
- **版本头（version header）**：每个槽 +0x1500000 的 512 B 块，含 serial / CRC1 / CRC2 / 槽表。
- **slot marker**：内核前的 32 B 标记（`3333cccc8888dddd` + 16×FF），cspboot 靠它认内核（树 fork image/Makefile:6-12）。
- **failsafe**：OpenWrt preinit 的救援 shell（本身不写 flash）。
- **类 1 / 类 2 故障**：见 §5.1。
- **bootIncl**：升级包版本头里的字段；为 0 表示包内不含引导区（E2631 全部现行包都是 0）。
